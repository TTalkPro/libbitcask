# S29-11 设计:HNSW 建图深层优化 + 向量驻留路线(与 DiskANN 深度对比)

> 状态:**预研,未立项(2026-07-11)**。来源:S29 四路热点分析(TASK.md
> S29-11 条目)。本文给出四个优化梯队的完整设计、实施顺序,以及「向量出
> 内存」路线与 DiskANN 的逐维对比——S30 之后 HNSW(图 + 向量)是本库
> **最后一个全量驻留内存的大轴**,该往哪个方向走需要先想清楚再动手。

---

## 1. 现状与根因

### 1.1 实测(S29 基线,6 核 @3.0GHz,无 AVX-512/VNNI,384 维)

| 指标 | 数值 | 含义 |
|---|---|---|
| `BM_Hnsw_Insert/10000` | ~3.0k docs/s | 建图基线 |
| `BM_Hnsw_Insert/100000` | 82s(1.2k/s) | **超线性变慢 2.5×** |
| 建图并行度 | 1 写者 | V3.3 `writer_active_` 单写者协议,6 核闲 5 |

### 1.2 根因链

1. **f32 导航工作集打穿 L3**:100k × 384d × 4B ≈ **153MB**(+ 邻接),
   L3 只有 24MB——每次插入的贪心下降在整图上随机跳,几乎每跳一次
   cache miss。规模越大 miss 率越高 ⇒ 超线性;
2. **int8 内核在无 VNNI 机器上缺位**:`pick_int8_dot_kernel()` 返回
   nullptr(现内核依赖 AVX-VNNI)⇒ 即使 V4.2 的 int8 量化副本(qcodes,
   dim+8 B/向量)在内存里躺着,建图/查询仍全程 f32;
3. **单写者**:V3.3 协议(`writer_active_` 哨兵)简化了并发模型,但建图
   吞吐被钉死在单核。

### 1.3 已到位、勿重复优化(S29 核实)

visited list 版本化复用、邻接 bump-arena、优先队列缓冲池、导航 prefetch、
`select_neighbors` thread_local 池(S29-3,已 -10%)。

## 2. 前置:召回评估基建(任何梯队开工前必做)

S29-11 的每一项都在「速度 ↔ 召回」上做交换,**没有召回标尺一切免谈**:

- 固定语料(如 100k × 384d 正态 + 真实语料抽样)+ 暴力精确 top-k 作
  ground truth(离线一次,缓存盘上);
- harness:`recall@10 / recall@100` × QPS × 建图耗时三元组,进
  bench(`hnsw_bench.cpp` 扩展)+ 数据存 `bench/baseline/`;
- 验收门:任何改动 recall@10 降幅 > 1pt 需显式声明并可配置回退。

## 3. 四梯队详设

### ① 配置级调参(成本最低,先拿数据)

- `ef_construction` 200→128、`M` 16→12 两档矩阵跑召回基建;
- 预期建图 1.5-2×,召回小降(文献与 hnswlib 经验)。**不改代码**,只给
  下游一组有据可依的推荐配置(wiser 场景:文本为主、向量为辅,可接受
  略低召回换建图吞吐);
- 产物:文档化的配置指引 + baseline 数据。

### ② 建图导航 int8 粗筛(核心项:双重收益)

**思路**:贪心下降/邻居选择的**距离比较**不需要 f32 精度——用已有的
int8 量化副本(qcodes)算内积做导航与候选排序,只在**最终邻居精选/
结果重排**时用 f32 精算。工作集 153MB → **38MB**(384B→96B/向量,
含 scale/sum),L3 命中质变。

- **AVX2 int8 内核**(无 VNNI 机器的缺口):`vpmaddubsw + vpmaddwd`
  经典两步(u8×s8 → s16 横加 → s32),对称量化下需处理符号(现
  V4.2 量化是对称 s8,可用 `vpsignb` 转换或改用 s8×s8 的
  `vpmaddubsw` 变体+偏置);~150 行,独立对拍(vs 标量参照,全值域);
- **精度策略**:导航层(L1+)全 int8;L0 的 ef 候选集仍 int8 排序,
  仅对**入选邻居**(M 个)与**返回 top-k** 用 f32 复算(inmem_int8
  模式已证明纯 int8 端到端召回可接受——本项是混合精度,召回损失
  应更小,由召回基建验证);
- **与 inmem_int8(P5)的关系**:P5 是「不存 f32」的内存模式(仅
  kDot);本项是「存 f32 但导航用 int8」的速度模式,两者共享内核与
  qcodes 基建,正交可叠加配置。

### ③ 并行插入(收益上限最大,工程量最大)

- 打破 V3.3 单写者:hnswlib 成熟方案——**per-node 邻接锁**(插入改
  某节点邻居表时锁该节点)+ entry point/最高层原子更新 + 图生长
  (新 chunk)的发布协议(本库 NodeChunk 追加不搬移,天然友好);
- 影响面审计(立项时逐项过):查询并发(现无锁读依赖单写者不变量
  ——需改为读者容忍邻居表瞬时不一致,hnswlib 同款语义)、
  `clone_live`/checkpoint(需静止点,现有 drain 机制可复用)、
  vector plugin 的 delta 链序列化(单调 ord 语义与乱序插入的关系,
  参考 S27-4 DWPT 的 LSN 守卫经验);
- 预期:近线性扩展(6 核 ~4-5×),叠加 ② 后建图吞吐量级改善;
- 风险最高:并发图结构 + TSan 全量 + 召回回归三重验收。

### ④ `dist_` 去虚(顺手项)

函数指针 → 模板实例/编译期分派(metric 在 open 时定死),每距离调用
省一次间接跳转与分支预测失败;文献与 S29 估计~几个 %。与 ② 合并做
(内核选择逻辑本来要动)。

**实施顺序**:召回基建 → ①(纯数据)→ ②+④(一批)→ ③(独立大项)。

## 4. 向量驻留路线:与 DiskANN 深度对比

S30 解决了倒排的内存问题;向量轴的「出内存」是下一个大决策点。业界
标杆是 **DiskANN**(Subramanya et al., NeurIPS'19;FreshDiskANN'21 增量
版)。先解剖它,再对比本库路线。

### 4.1 DiskANN 架构解剖

- **图**:Vamana——**单层**近邻图,α-RNG 剪枝(α>1 保留部分"绕路"边
  充当长程捷径,替代 HNSW 的层级结构);度数上限 R(≈64);
- **盘上布局**:每节点一个对齐块:`[f32 向量 | 邻接表]` **共置**——
  一次 SSD 读同时取到"算距离所需"与"下一跳所需"(这是 DiskANN 的
  灵魂:每跳恰好一次 IO);
- **内存驻留**:每向量一个 **PQ 压缩码**(乘积量化,典型 32-64B,
  比原向量小 20-50×)+ 少量缓存的热节点(入口附近);
- **搜索**:beam search——用 RAM 的 PQ 近似距离决定"值得展开的 W 个
  候选",**并发发起 W 路 SSD 读**(NVMe 队列深度吃满),取回的全精度
  向量做重排;典型配置 W=4-8,每查询几十次 IO,延迟 1-5ms(NVMe);
- **构建**:全量数据多趟(随机图 → 两轮 α 剪枝),内存峰值高——大库
  分片建再合并;
- **更新(FreshDiskANN)**:盘上主图**不可变**,增量写进 RAM 的
  临时索引,后台 StreamingMerge 周期性把 delta 合并进主图 + 墓碑删除
  ——**与本库段模型(building/sealed/merge)完全同构的心智**。

### 4.2 逐维对比:DiskANN vs 本库现状 vs 本库可选路线

| 维度 | DiskANN | 本库 HNSW 现状 | 本库路线(见 4.3) |
|---|---|---|---|
| 图结构 | Vamana 单层 α-图 | HNSW 多层 | 保持 HNSW(重写图算法收益不明) |
| 向量驻留 | PQ 码(32-64B)RAM;f32 盘上 | f32+int8 全驻留(或 inmem_int8:仅 int8,-80%) | int8(dim+8 B)RAM;f32+邻接 mmap |
| 图驻留 | 盘上(与向量共置) | RAM | mmap(页缓存管冷热) |
| 每查询延迟 | 1-5ms(几十次 NVMe IO) | ~µs-百 µs(纯 RAM) | 热:≈现状;冷:页错误,亚 ms |
| 导航距离 | PQ 近似(~5-10% 误差)+ 重排 | f32 精确 | int8 近似(~1% 误差)+ f32 重排 |
| 内存/百万向量(384d) | ~48MB(PQ48) | ~1.6GB(f32+int8+邻接) | ~100MB(int8+scale) |
| 规模甜区 | 十亿级/单机 SSD | 百万级 | 千万级 |
| 增量更新 | 主图不可变+RAM delta+后台 merge | 原地插入(单写者) | 原地插入不变;mmap 段随 ckpt 重写 |
| 崩溃恢复 | 快照+delta 重放 | WAL 重放 + qc8/ckpt(现成) | 同左(基建复用) |
| 依赖/工程量 | PQ 训练+IO 调度+分片构建(重) | — | 复用 S30 mmap 模式(中) |

### 4.3 关键洞察与本库路线

1. **本库已经走在「DiskANN 的一半」上**:V4.2 int8 副本 + P5 inmem_int8
   = "RAM 侧压缩表示"(角色等同 DiskANN 的 PQ-in-RAM,且 int8 的距离
   误差(~1%)远小于 PQ(5-10%),不需要训练码本);缺的是另一半——
   **f32 与邻接出内存**。
2. **「DiskANN-lite on mmap」是与 S30 一致的低成本路线**:
   - 盘格式:HNSW 图按节点共置布局 `[邻接 | f32 向量]`(DiskANN 的
     布局智慧直接借用),对齐页,checkpoint 时整体重写(现 BVH2/qc8
     序列化已有雏形,改布局即可);
   - RAM 驻留:int8 码 + scale(导航距离全部在 RAM 完成,**不触盘**)
     + 上层图(层级图的 L1+ 节点数 ≈ N/M,很小,常驻);
   - 搜索:导航用 int8(纯 RAM)→ L0 候选确定后,**只对 ef 个候选**
     触 mmap 读 f32 重排——每查询页错误数 ≈ ef(冷)/0(热),页缓存
     天然充当 DiskANN 的"热节点缓存";
   - 与真 DiskANN 的差距:无显式 beam IO 并发调度(依赖页缓存/预读),
     无 PQ 级压缩比。**在千万级、NVMe、int8 导航把触盘次数压到 ef 级
     的前提下,这个差距可接受**;十亿级需求出现才值得引 Vamana+PQ+
     显式 IO,那是完全另一个量级的工程。
3. **FreshDiskANN 的更新模型我们不需要抄**——它解决"盘上主图不可变
   如何增量"的问题;本库向量插入走 WAL+内存图,mmap 化后 ckpt 重写
   整图文件(向量图不像倒排段可多段归并——HNSW 是单一全局图),
   增量语义由既有 WAL 重放 + delta 链承担。**若未来图大到 ckpt 重写
   不可承受,才需要向量版段模型(delta 图 + 定期全量合并),届时
   FreshDiskANN 是直接参考**。
4. **依赖关系**:S29-11-②(AVX2 int8 内核 + 混合精度导航)是建图提速
   与向量出内存的**共同前置**——先做它,两条路都通。

### 4.4 路线结论

```
S29-11-② int8 混合精度(共同前置)
   ├─▶ 建图提速线:①调参 → ④去虚 → ③并行插入
   └─▶ 驻留线(S32 候选):图+f32 共置 mmap,RAM 只驻 int8+上层
        (DiskANN-lite;十亿级需求出现前不引 Vamana/PQ/显式 IO)
```

## 5. 验收标准(各梯队通用)

- 召回基建三元组(recall@10/100 × QPS × 建图耗时)相对基线出数;
- recall@10 降幅 >1pt 需显式配置项承载;
- ③ 并行插入:TSan 全量 + 定向并发压力(插入 vs 查询 vs clone_live);
- 驻留线:RSS 探针(同 S30 方法论)+ 冷/热查询延迟分布。

## 6. 风险

- ② 的混合精度召回回归——由召回门槛兜底,可按 metric/维度配置回退;
- ③ 打破单写者是全库最高风险并发改动之一,必须独立批次 + 评审;
- 驻留线的冷查询长尾(页错误)——与 S30 相同权衡,int8 导航把触盘
  压到 ef 级是成立前提,立项时先用实验证实这一点再动格式。
