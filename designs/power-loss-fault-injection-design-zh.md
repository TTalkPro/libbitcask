覆盖面比 libbitcask 现有的「杀子进程」式崩溃测试大得多。
关联：`include/bitcask/io.hpp` / `src/io/posix_file.cpp`（宿主文件原语的唯一出口）、`include/bitcask/detail/file_util.hpp`
（`AtomicFileWriter` 等 `FILE*` 写入）、`tests/support/crash_child.hpp` 与 `tests/crash_recovery_test.cpp` /
`index_crash_recovery_test.cpp` / `checkpoint_recovery_test.cpp`（现有崩溃测试）。

## 1. 结论（先说推荐）

- **推荐方案 A：在 io 层加「写操作录制」钩子，测试侧按掉电语义从录制里生成崩溃镜像，再对每个镜像做恢复 + 不变式检查。**
  引擎照常对真实文件读写，钩子只是旁路记账；不虚拟化读路径，不改任何盘上格式，生产构建里钩子是一个恒为空的原子指针。
- 检查的不变式一句话：**任何时刻掉电后重开，库恰好等于「某个已提交写操作的前缀」，前缀不短于最后一次成功 `sync` 时的内容；
  原子批不出现半个；各派生索引与 data 一致。**
- 分三期：先把落盘入口收拢 + 录制 + 「按序前缀」崩溃（一期，收益最大）；再加乱序与扇区撕裂（二期）；
  最后是恢复过程中的二次掉电与常驻随机种子（三期）。

## 2. 现状与缺口

### 2.1 今天怎么测崩溃

- `tests/support/crash_child.hpp`：fork 一个子进程跑场景函数，在选定位置 `crash_exit()`（不 close、不析构）。父进程重开目录核对。
- 另有手工构造的损坏：`CrashRecoveryTest.TornWriteTruncated` 直接把文件尾截掉半条记录；注入矩阵（S43）改索引里的定位。

这等价于「**进程被杀**」：进程死的那一刻，已经 `write` 进内核的字节全部还在，文件长度、目录项、重命名也都生效。

### 2.2 测不到的

真正的掉电 / 内核崩溃与「进程被杀」差在页缓存：

| 掉电后可能出现的状态 | 杀进程能否造出 |
|---|---|
| 最后一次 fsync 之后的写**全部丢失** | 不能（都还在） |
| 其中**一部分**落盘、且**与写入顺序无关**（先写的没落、后写的落了） | 不能 |
| 一次写只落下**若干个扇区**（记录中间撕裂、头尾在而中间是旧内容） | 不能（只能手工造「尾巴少一截」） |
| 文件**长度已增长但数据没落**（读回来是零） | 不能 |
| `rename` / 新建 / 删除已返回，但目录没 fsync，**目录项回退** | 不能 |
| 截断没生效 | 不能 |
| 恢复做到一半**再掉一次电** | 不能 |

这些正是下面这些路径的正确性所依赖、而今天只靠代码审查保证的地方：

- 原子批的「批头 + 成员同一次 flush = 提交点」（S35）；
- OKI 的「run 落盘 → manifest 提交 → 推进水位」与持久水位过滤（S36-5 B1、S44）；
- `AtomicFileWriter` 的 tmp → fsync → rename → fsync 目录；
- 检查点里 docmap / bm25 / 向量各文件之间的先后；
- `bitcask.meta` 懒升级（v6 / v7）先于首个批字节；
- S65 新加的活跃文件映射读（读到的必须是已写出的字节）。

顺带：反馈 `feedbacks/2026-11-23-recovery-truncates-synced-data-on-bad-record-header.md`（恢复把已落盘区间当尾巴截掉）
这类问题，掉电模型的「扇区撕裂落在记录头上」一类用例本可以自己撞出来。

## 3. 目标与不变式

对「一段写负载」与「它执行期间的任意一个掉电点」，重开后必须同时满足：

1. **打得开**：`Cask::open` 成功，或以明确的损坏码失败且不改动任何文件（后者只允许出现在模型注入了「已同步数据被破坏」的用例里，
   正常掉电模型下必须成功）。
2. **前缀一致**：存在一个 k，使库的内容（全部 key 的值与 LSN）恰好等于「负载的前 k 个已提交操作依次生效」的结果。
3. **持久性下界**：k ≥ 掉电点之前最后一次成功返回的 `sync()` / `checkpoint()` / `o_sync` 写所覆盖的操作数。
   （`sync_every_n` 等策略按各自承诺折算。）
4. **原子批不拆**：`put_batch_atomic` / `TxnCask::commit` 的成员要么全在、要么全不在。
5. **派生一致**：OKI（点查、range、迭代器三方对拍）、docmap、全文与向量索引给出的结果与 data 里胜出的记录一致；
   `flush_index()` 能返回。
6. **可继续写**：重开后再写一批、再 close、再重开，仍满足 1～5（验证恢复没有留下坏状态）。
7. **不越界删除**：恢复过程不删、不截断任何「掉电点之前已同步」的字节（由模型核对：恢复期间的截断 / 删除操作与同步水位比较）。

## 4. 方案

### 4.1 方案 A：io 层录制 + 镜像生成（推荐）

三个部件：

**① 录制钩子（库内，极薄）**

`src/io` 里所有会改变持久状态的原语在成功返回后调一次钩子：

```cpp
namespace bitcask::io::fault {
enum class Op : std::uint8_t { kCreate, kWrite, kTruncate, kSyncFile, kSyncDir, kRename, kRemove };
struct Event {
    Op op;
    FileIdentity file;          // 设备 + inode（rename 后仍能对上）
    std::string path, path2;    // 发生时的路径；rename 的目标
    std::uint64_t offset = 0;
    std::uint64_t length = 0;   // kTruncate：新长度
    std::vector<std::byte> data; // kWrite：写入的字节
};
using Sink = void (*)(const Event&, void* ctx);
void set_sink(Sink, void* ctx) noexcept;   // nullptr 关闭；生产构建里恒为 nullptr
}
```

要覆盖的入口（现状盘点）：

| 入口 | 现状 | 要做的 |
|---|---|---|
| `File::pwrite` / `write`、`pwrite_all`、`truncate_handle`、`sync_data`、`sync_directory`、`atomic_rename`、`remove_file` | 已集中在 `src/io` | 加钩子调用 |
| `FILE*` 写入（`fopen_utf8` + `fwrite` + `fflush`，约 33 处，主要经 `AtomicFileWriter`） | 在 `detail/file_util.hpp` | 把落盘动作收进 2～3 个包装函数（写、flush、fsync），包装里调钩子 |
| `std::filesystem::remove`（约 30 处） | 散在各模块 | 改走 `io::remove_file`（多数是清理临时文件，机械替换） |
| `std::filesystem::rename` | 已只剩注释里提到，实际走 `atomic_rename` | 无 |
| 可写映射 | 无（只读映射） | 加一条静态检查，防止以后引入 |

钩子是一个原子函数指针，空时只多一次判空分支。不做编译开关也可以；若担心，可用 `BITCASK_FAULT_INJECTION` 宏在发布构建里整个抹掉。

**② 磁盘模型（测试侧，`tests/support/disk_model.hpp`）**

把事件流重放成「掉电后盘上可能的状态」：

- 每个文件维护：已同步内容（最后一次 `kSyncFile` 时的字节与长度）、之后的未同步写列表、目录项是否已随 `kSyncDir` 持久。
- 给定掉电点 t（事件序号）与崩溃风格，生成一个目录镜像：

| 风格 | 未同步写的命运 | 对应现实 |
|---|---|---|
| `kProcessKill` | 全部保留 | 进程被杀（与现有测试等价，作基线） |
| `kPrefix` | 保留按时间序的一个前缀；前缀的最后一次写可只落前半（按扇区对齐截断） | 顺序落盘的设备 |
| `kSubset` | 任取子集，顺序无关 | 页缓存乱序回写 |
| `kSectors` | 每次写按 512 字节扇区拆开，任取扇区子集 | 撕裂写 |

- 另外三个开关：长度增长但数据未落（读回零）；截断未生效；未 `kSyncDir` 的新建 / 重命名 / 删除回退。
- 全部由一个种子驱动，失败时打印种子、掉电点与风格，可单条重放（环境变量 `BITCASK_PL_SEED` / `_CUT` / `_STYLE`）。

**③ 负载与检查器（测试侧，`tests/power_loss_test.cpp`）**

- 负载是一段确定性的操作序列（由种子生成）：`put` / `remove` / `put_batch_atomic`（含条件）/ `put_doc`（检索库）/ `sync` /
  `checkpoint` / roll（小 `max_file_size`）/ `merge`。同时在内存里维护「影子」：每个操作提交后的全量状态快照（或增量），
  以及每次成功 sync 时已提交的操作数。
- 录制一遍得到事件流（一次负载只录一次）；然后对选定的掉电点 × 风格 × 种子生成镜像，逐个执行第 3 节的检查。
- 掉电点的选取：每个 `kSyncFile` / `kSyncDir` / `kRename` 的**前后各一个**（确定性，覆盖所有提交点），外加随机点。

**为什么是「录制 + 生成镜像」而不是完整的虚拟文件系统**（LatticeDB 的做法）：LatticeDB 的引擎全程经一个 VFS 接口做 I/O，
换实现很自然；libbitcask 的 `File` 是对句柄的薄封装，读路径还有映射（sealed 文件、S65 的活跃文件）。虚拟化读路径要动的面很大，
而掉电测试并不需要拦读——镜像生成之后是用**真实文件**重开的，读路径原样被测到。

### 4.2 方案 B：`LD_PRELOAD` 拦系统调用（不推荐）

不改库，拦 `pwrite` / `fsync` / `rename` …。问题：`fwrite` 在 libc 内部发起的 `write` 拦不到（不经 PLT）；
只能在 Linux 上跑；与 ASan / TSan 的拦截器互相打架。

### 4.3 方案 C：外部工具（dm-log-writes、CrashMonkey 一类，不推荐作主力）

内核块层录制，最真实。但要 root 与专用块设备，进不了日常 `ctest`，也没法在 FreeBSD / Windows 上跑。可以留作发版前的偶尔抽查，不是这份设计的范围。

## 5. 细节

### 5.1 文件身份

事件用（设备，inode）标识文件，另带发生时的路径。`rename` 之后同一个 inode 换了名字，模型按 inode 跟踪内容、按目录项跟踪名字；
`AtomicFileWriter` 的 tmp → 最终名因此能正确表达成「内容已同步、但改名未必持久」。

### 5.2 录制的体量

每次写要拷一份字节。负载规模控制在几千个操作、数据量几 MB 即可覆盖全部提交点（roll 用小 `max_file_size` 逼出）；
事件流常驻内存。大规模随机负载留给三期的夜间任务。

### 5.3 检查器怎样判「前缀」

不逐个尝试 k。读出库里全部 key → (value, LSN)，取最大 LSN 对应的操作序号 k'，再核对整库与影子在 k' 处的快照逐 key 相等
（LSN 是按提交顺序分配的，S46 的契约保证重开后不变）。原子批的成员共享一个提交点，自然被这条覆盖。

### 5.4 与 sync 策略的关系

- 缺省（不主动 sync）：下界是最后一次 `sync()` / `checkpoint()` / close；之间的写允许丢，但必须整段丢在尾部。
- `o_sync`：每个返回成功的写都在下界之内。
- `sync_every_n`：下界按「每 n 条一次 fdatasync」折算。
- 检索库：索引是派生数据，允许落后于 data，但重开后必须追平（第 3 节第 5 条）。

### 5.5 二次掉电（三期）

对镜像执行 `open` 时再录制一遍恢复过程的写（恢复会截断尾巴、重建索引、写 manifest），在恢复的事件流上再选掉电点生成二级镜像，
对二级镜像重复检查。验证恢复本身是可重入的。

### 5.6 平台

录制钩子与磁盘模型不依赖平台。Windows 上文件身份用卷序列号 + 文件索引（`handle_identity` 已有）。
「目录项回退」在 Windows / NTFS 上语义不同，Windows 上先只跑 `kProcessKill` 与 `kPrefix` 两种风格。

## 6. 预期会撞出什么

诚实地说，不知道。这类测试第一次接入通常会报出一批问题，其中一部分是真缺陷，一部分是「文档没承诺、实现也没做」的灰色地带
（例如不主动 sync 时 roll 出来的新文件目录项没持久）。设计上先把这类发现分成三类处理：

1. 违反已有文档承诺 → 当缺陷修；
2. 文档没承诺 → 先补文档写清楚承诺到哪一步，再决定是否加强；
3. 模型过严（现实设备不会出现）→ 放宽模型并注明依据。

## 7. 不做的

- 不模拟介质错误（读返回 EIO、静默位翻转）。那是另一类测试；现有注入矩阵覆盖了一部分。
- 不改盘上格式、不改任何恢复逻辑——这份设计只加测试设施。测出来的问题另行立项。
- 不追求穷举：掉电点 × 子集是指数的，靠「全部提交点 + 随机采样 + 可重放种子」覆盖。
