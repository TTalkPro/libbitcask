# OKI 分级归并（Size-Tiered Suffix Compaction）设计

状态：设计稿（未实现） · 2026-11-16 · 同日完成一轮自审（第 10 节），4.5 / 4.7 / 4.8 / 第 8 节据此修订；并入「读视图整体不可变发布」（4.9，作为前置阶段 T-0）
关联：`doc/ordered-key-index-design-zh.md` §5.2（极简两层归并）、`src/fileops/oki_state.cpp`（`compact_runs`）、`include/bitcask/oki_merge_cursor.hpp`

## 1. 结论

把 OKI 的 run 归并从「run 数 > 8 就把**全部** run 重写成一个」改成**分级后缀归并**：

```text
run 序列（按 gen 升序）： R0(底座, 最大) R1 R2 … Rn(最新, 最小)
每次只归并「最新的一段连续后缀」Rj..Rn，选段规则是几何的：
    从 Rn 往前累加，前一个 run 不比已累加的后缀大太多就并进来
后缀延伸到 R0（底座）时才是「全归并」，才允许丢墓碑
```

效果：

- 索引写放大从 **O(N / 每次 flush 行数)** 降到 **O(log(N / 每次 flush 行数))**，与库的总规模基本脱钩；
- **不改盘上格式**：manifest、run 文件、恢复流程都不变；新旧版本库可以互相打开同一目录；
- 代价是常驻 run 数从「≤ 9」变成「≤ log₂(N/F) + 1」（1 亿 key 时约 8～12 个），点查多几次内存 bloom 判定。

## 2. 现状与问题

### 2.1 现状（本轮修复后）

- memdelta 达到 1M 行 / 64MiB，或任一提交点（close / checkpoint / merge 收尾 / 备份）→ flush 出一个新 run；
- flush 提交后 run 数 > `kCompactRunLimit`（8）→ `compact_runs`：三段式（锁内快照输入 + 预留 gen → 锁外 `OkiMergeCursor` 归并写新 run → 锁内校验并替换），IO 段不持 `flush_mu_`；写线程上的阈值 flush 把归并交给后台线程；
- 全归并 ⟹ 墓碑真正丢弃（同 key 的 put 行与墓碑行必在同一次归并里）。

### 2.2 问题：每次都搬一遍不变的底座

每次归并都重写**整个索引**（O(N)），但两次归并之间新进来的只有约 8 个 run（8·F 行，F = 单个 run 的行数）。每写入一行，平均被重写的次数：

```text
写放大 ≈ N / (8·F)
```

F 不是常数：阈值 flush 是 1M 行，但 OKI flush 也搭在 base checkpoint、close、merge 收尾上——搜索模式默认每 65536 条触发一次自动 checkpoint（`auto_checkpoint_min_docs`），run 往往远小于 1M。

| N（活 key） | F = 1M | F = 64K | 单次全归并重写量（~15B/行） |
|---|---|---|---|
| 1000 万 | ~1.3× | ~19× | ~150MB |
| 1 亿 | ~12× | ~190× | ~1.5GB |
| 10 亿 | ~125× | ~1900× | ~15GB（分钟级） |

本轮已把归并挪到后台、IO 不持锁，所以它不再卡住写者和读者；但磁盘带宽和写放大仍随 N 线性增长。搜索模式下 1 亿 key 量级就已经明显浪费。

## 3. 目标与非目标

**目标**

1. 写放大与总规模脱钩：≈ log₂(N/F) 量级。
2. 盘上格式零改动（manifest v4、run v3 不变），升级/降级都不需要迁移。
3. 正确性不变量（gen 优先级、墓碑语义、提交一致性）与现状同等强度，且可测试。
4. 常驻 run 数有硬上限，点查读放大可控。

**非目标**

- 不做 leveled（分层、key 区间不重叠）——需要 manifest 记录层级和区间、点查逐层查，改动大，十亿级以上再议；
- 不做按 key 区间的分区归并；
- 不改 memdelta flush 阈值、不改 run 文件格式。

## 4. 设计

### 4.1 关键约束：只能归并「连续后缀」

OKI 的胜出规则是 max (ord, 来源序)：同 ord 时 gen 更高的 run 胜。同 ord 的多行只来自 merge 搬迁（`relocate` → `append_update`）：旧位置在较老的 run，新位置在较新的 run。

若归并**不连续**的一组 run（例如 R3 和 R5，跳过 R4），输出拿到新的最大 gen，R3 里的旧位置就会压过 R4 里的新位置——输入文件退役后索引悬空。若归并**中间一段**（R2..R4，后面还有 R5），输出 gen 必须落在 (gen(R4), gen(R5)) 之间，整数 gen 做不到。

因此规定：**每次只归并 Rj..Rn 这一段后缀**，输出取新的最大 gen。

- 输入之后在归并期间新 flush 出的 run，其 gen 由「在途预留」机制保证大于输出 gen（现有 `inflight_gens_`），依然排在输出之后；
- 比 Rj 更老的 run 不动。

这样「gen 越大越新」的不变量在任何时刻都成立，`locate`（gen 降序首命中）、`OkiMergeCursor`、`make_read_view`、恢复流程都不需要改。

### 4.2 选段规则（几何后缀）

记 run 大小 sᵢ = `OkiRunReader::entry_count()`（行数，含墓碑行），R0..Rn 按 gen 升序。

```text
j = n, acc = s_n
while j > 0 and s_{j-1} <= K * acc:      # K = 扇入系数，默认 1
    j -= 1; acc += s_j
if n - j + 1 >= 2: 归并 Rj..Rn
```

直观理解（K = 1）：从最新的 run 往前看，只要前一个 run 不比后面已攒起来的总量大，就把它并进来。这就是二进制计数器式的合并——每行每次被重写时所在 run 的规模至少翻倍，所以一行最多被重写约 log₂(N/F) 次。

- K 越大越激进（run 数更少、写放大更高）；K → ∞ 退化为现在的全归并。默认 K = 1，留作调参点。
- 何时检查：每次 flush 提交后（与现在的触发点相同）。flush 持锁算出是否需要归并，归并本身仍走三段式（阈值 flush 交后台，其余提交点在释放锁后同步做）。
- 后台线程收尾时复查并续跑（沿用本轮已实现的循环）。

### 4.3 硬上限与全归并

- **run 数硬上限** `kMaxRuns`（默认 24）：几何规则在病态输入下（例如 flush 大小剧烈波动）仍可能积累较多 run；超过上限时强制把后缀扩到满足上限为止。
- **全归并**（后缀覆盖到 R0）照旧由几何规则自然触发：后缀累加量追上底座（K = 1 时即新增量 ≥ 底座）时。
- **墓碑占比过高时的显式全归并**：墓碑行只在全归并时回收。若在后缀归并时发现「输出中墓碑行 / 总行」超过阈值（默认 25%），把下一次归并标记为全归并。墓碑计数在归并过程中顺带统计，不需要改 run 格式。
- 保留一个内部开关 `CompactionPolicy::kFull`，用于 A/B 基准对比和回退。

### 4.4 墓碑处理

| 归并范围 | 墓碑行 | 原因 |
|---|---|---|
| 后缀包含 R0（全归并） | 丢弃（同现状） | 同 key 所有更老的行都在输入里，put 与墓碑一起消失 |
| 不含 R0 的后缀 | **必须保留**，原样写入输出 | 更老的 run 里可能还有该 key 的 put；丢掉墓碑会让它「复活」 |

实现上：`OkiMergeCursor::next(row, include_tombs = !full)`，输出 run 对墓碑行写 `tomb=true`、不带位置（与 flush 产出的墓碑行同形）。

同 key 在后缀内既有 put 又有更新的墓碑时，后缀内的胜出者是墓碑，put 行被抵消；输出只留一条墓碑行。这正是现有 flush 的去重语义。

### 4.5 提交与并发（沿用三段式）

在 `compact_runs` 的基础上泛化：

1. **锁内**：按 4.2 / 4.3 选出后缀 Rj..Rn（以及是否全归并），快照这些 Reader，预留输出 gen（登记为在途）。
2. **锁外**：`OkiMergeCursor` 归并后缀，按 4.4 处理墓碑，写出输出 run，fsync，打开 Reader 校验。
3. **锁内**提交前校验：
   - 输入 gen 仍全部在册，且仍构成「当前 run 序列中、所有新于输出 gen 的 run 之前」的一段连续区间（期间只可能在其后追加新 run）；
   - 期间若发生 rebuild（run 集合被整体替换）、或别的归并改动了输入 → 放弃，删除输出；
   - 新 manifest = 当前 manifest 中 Rj 之前的 run + 输出 + 期间新增的更高 gen run；元数据 / fstats / data 水位 / wm 原样沿用（与本轮修复后一致）。
4. 发布 run 快照 → sweep 输入文件（在途构建的 gen 受保护）→ 块缓存清掉死 gen。

读视图无锁构建（「先取 delta、后取 runs」）的正确性论证不变：归并只替换 run，不动 delta。

**并行度：两条归并道**（自审修订，原稿是「同一时刻至多一个归并」）。只允许一个归并时，一次大归并（十亿级全归并是分钟级）期间所有小归并都被挡住，run 数、fd、点查读放大在这段时间里无界增长，`kMaxRuns` 形同虚设。修订为：

- 一个归并在途（预留输出 gen = G）时，允许再起一个「年轻道」归并，但它**只能取 gen > G 的 run**（在途归并开始之后才 flush 出来的那些）。这些 run 仍是当前序列的连续后缀，输出 gen 仍是新的最大值，4.1 的不变量不受影响；
- 年轻道永远不含 R0，必然保留墓碑；
- 两道各自提交、互不依赖：老道提交时把自己的输入替换成输出并保留其后的所有 run（可能已是年轻道的输出）；年轻道提交时只替换自己的输入；
- 仍不够时（run 数 > `kMaxRuns`）对 flush 施加背压（见 4.8）。

### 4.6 与其它机制的交互

- **merge 搬迁行**：同 ord 的新位置总在更新的 run（或 delta）里；后缀归并保持相对顺序，搬迁裁决不受影响。
- **rebuild**：产出单一 run（即新的 R0），之后从头开始分级。
- **恢复**：manifest 与 run 格式不变，data-only 恢复、`recover_row` 的视图比对、账本模式补 tail 全部不变。
- **v1 run**：含 v1 输入时输出降为 v1（同现状）；只要 v1 run 还没被 rebuild 淘汰，点查不可用的语义就不变。
- **降级兼容**：旧版本库打开新目录时，看到的是若干按 gen 升序的 v3 run（非底座 run 里带墓碑行，和 flush 出的 run 同形），完全可读；旧版本下次归并会做全归并，也正确。

### 4.7 并发读正确性（逐读路径论证）

归并期间有四类读者，逐一说明为什么读不到错数据，以及各自依赖的不变量。

**依赖的不变量**

- **I1（gen 序）**：对任一 key，gen 更高的 run 里的行不旧于 gen 更低的 run 里的行（ord 更大，或 ord 相等且是更新的信息）。后缀归并 + 输出取最大 gen 保持 I1（4.1）。
- **I2（内容等价）**：归并前后的 run 集合，对任一 key 给出相同的裁决结果。不含 R0 的归并保留墓碑，故等价；含 R0 的归并丢弃墓碑时，被墓碑压住的旧行也一并消失，结果同为「不存在」。
- **I3（成对提交）**：凡同时改动 runs 与 delta 的提交（flush 的「发布 run + 裁前缀」、rebuild），对读视图成对可见（`SeqGate`：`view_gate_`）。归并只换 runs，不进窗口。

**四类读者**

| 读者 | 取数方式 | 为什么正确 |
|---|---|---|
| 点查 `locate` | 先查 delta 哈希，未命中再取一次 runs 快照，gen 降序首命中 | runs 快照是不可变整体，归并提交是一次原子替换，读者看到的要么全是旧集合、要么全是新集合（I2 保证两者等价）；「首命中即权威」依赖 I1 |
| 写前探测 `probe_for_write` | 同 `locate`，且在写序闸门内 | 同上；归并不改变任何 key 的裁决结果，CAS 判定不受影响 |
| 读视图（range / fold / merge 的 `make_read_view`） | (delta 快照, runs 快照) 成对 | I3 保证两者属于同一提交点之间的状态；归并换 runs 与任一时刻的 delta 组合都自洽（I2） |
| 在途迭代器 | 持有旧 Reader 的共享所有权 | 旧 run 文件 unlink 后 fd 仍可读；看到的是创建时刻的一致快照 |

**必须写进测试的三个陷阱**

1. **不含 R0 的归并丢了墓碑** → 破坏 I2：底座里的旧 put 重新可见，读者读到**已删除的旧值**。这是本方案里最危险的一类错读（4.4 的规则 + 模型对拍专项）。
2. **归并了不连续或非后缀的 run** → 破坏 I1：`locate` 首命中拿到旧位置；读视图里旧位置在等 ord 时压过新位置。读者按旧位置去读已退役的 data 文件（4.1 的约束 + 提交时连续性校验）。
3. **读视图的 (delta, runs) 不成对** → 等 ord 判反。这一条在现有代码里已经出现过：把 `make_read_view` 改成不持 `flush_mu_` 时只保证了不缺行，没有保证成对，旧 delta 里的原始行会压过新 run 里同 ord 的搬迁行 / 条件墓碑。已在代码里修复（flush 的发布与裁剪纳入 `SeqGate` 写窗口，即 `view_gate_`）。本方案**不得**为了省事把归并提交也做成「改 runs 的同时动 delta」，否则要同样进窗口。

**`locate` 首命中的额外核对**：实现时加一个调试期断言 / 对拍——对同一 key，`locate` 的结果必须与 `OkiMergeCursor` 在同一视图上的裁决一致。两者是 I1 的两种消费方式，任何破坏 I1 的改动都会让它们分叉。

### 4.8 运行约束（自审补充）

- **归并一律走后台**。现状里只有写线程上的阈值 flush 把归并交后台，checkpoint / close / merge 收尾是同步归并。分级之后归并更频繁，且偶尔会轮到一次大归并；自动 checkpoint 跑在索引 reducer 线程上，同步归并会把整条索引流水线卡住。修订：所有提交点都只「调度」归并；需要确定性 run 集合的调用方（测试、基准）用 `wait_compaction()`。
- **可取消**。`OkiState` 析构（close 的最后一步）要等后台归并线程；大归并不可取消的话 close 会卡几分钟。归并循环每写 N 行检查一次取消标志，取消即删除半成品输出——输入未动，没有任何副作用。
- **背压**。run 数超过 `kMaxRuns` 时，flush 提交后同步等待年轻道归并完成（写者短暂减速），而不是继续堆 run。
- **run 数上界取决于最小的 run，而不是典型的 run**。close / 小 checkpoint 会产出只有几行的 run，几何规则下它们彼此很快合并，但上界公式里的 F 要按最小 run 算（log₂(N/1) ≈ 27～30）。`kMaxRuns` = 24 在这种情况下会触发强制合并，这是预期行为，不是异常。
- **跨进程读者**。只读句柄和 merge_only 旁车在自己的进程里 `load`：先读 manifest，再逐个打开 run 文件。归并提交后立刻 sweep 输入文件，另一个进程可能刚读完旧 manifest、还没打开 run——打开失败后当前实现会退回「未加载 → 全量重建内存视图」。分级后归并频率更高，这个窗口被撞上的概率随之上升。应对：`load` 遇到 run 文件缺失时重读 manifest 重试（有界次数），而不是直接放弃。
- **Windows**。打开中的文件 unlink 会失败，输入 run 进 `sweep_backlog_` 延迟删除。归并更频繁 → 滞留文件更多；需要确认 backlog 重试点足够密（每次归并提交都会重试，应当够用，但要有测试覆盖）。

### 4.9 读视图整体不可变发布（前置阶段 T-0）

**动机。** 现在读视图由两份各自独立发布的状态拼成：run 集合（`SnapshotCell<RunsVec>`）和 memdelta（`mu_` 下的可变数组）。二者「成对」靠 `SeqGate` 校验加重试——所有同时改动两者的提交点都必须记得进窗口，4.7 的 I3 是一条靠纪律维持的不变量。分级归并让提交点变多、变频繁（两条归并道、后台化），与其继续加窗口，不如让「成对」由构造保证，把 I3 从纪律变成类型。

**数据模型。**

```text
OkiView（不可变，整体经 SnapshotCell<OkiView> 发布）
  ├─ runs            : [Reader…]         按 gen 升序
  ├─ frozen          : [DeltaSegment…]   已冻结、已排序去重的内存段（不可变），按冻结先后
  └─ frozen_through  : seq               「到达序号 ≤ 它的行已全部归入本视图」的水位

active memdelta（仍是 mu_ 下的可变结构，只追加）
  每行带到达序号 seq（DeltaRow::seq，已存在）
```

**读者**（点查、读视图一律如此，不重试、不进任何闸）：

1. 取 active 的快照（或查 active 哈希）；
2. `view = cell.load()`；
3. 丢弃 active 快照中 `seq ≤ view.frozen_through` 的行；
4. 按来源序裁决：active（过滤后）> frozen（新 → 旧）> runs（gen 降序）。

第 3 步是关键：无论读者拿到的 active 快照有多旧，凡是已经被归入视图的行都按 seq 被剔除，不会再以「内存行」的身份去压视图里同 ord 的更新行。上一轮修掉的等 ord 判反（旧 delta + 新 run）在这个模型里从构造上不可能出现。顺序仍须「先 active、后 view」：反过来会漏掉恰在两步之间被冻结的行。

**写者的三个发布点**（都在 `flush_mu_` 下「读当前视图 → 构造新视图 → 发布」）：

| 动作 | 新视图 | 说明 |
|---|---|---|
| 冻结（flush 开始） | `frozen += seg`，`frozen_through = S` | S = 本次提交切面的 `cut_seq`；seg = active 中 seq ≤ S 的行排序去重后的不可变段。发布之后再把这些行从 active 物理删除——删除早晚都不影响读者（第 3 步按 seq 过滤） |
| 落盘完成 | `runs += run`，`frozen −= seg` | **一次发布**取代现在的「发布 run + 裁 delta」两步，不再有中间态 |
| 归并提交 | `runs` 中输入换成输出 | frozen、frozen_through 原样带过去；两条归并道各自发布 |
| rebuild | `runs = [新 run]`，`frozen = []`，`frozen_through = 当前最大 seq` | active 里的旧行被水位整体作废，随后物理清空 |

**附带收益。**

- flush 的 IO 期间，被冻结的行以**已排序**的不可变段存在：这段时间的 range / fold 不再每次重排它们（现在靠 `sorted_view_` 缓存缓解，写一次就失效）；
- `SeqGate` 从 `OkiState` 里删掉，读视图不再有重试路径；
- 冻结后 active 立即变小，`delta_idx_` 的重建量只与新到的行有关。

**需要一并处理的点。**

- **持留行**：带提交切面的 flush 本来就以 `cut_seq` 划界（切面之后到达的行留下），与 `frozen_through = cut_seq` 天然一致。不带切面的旧路径（按持久水位整组持留）会让「seq ≤ S 的行仍留在 active」，破坏水位语义——该路径只有测试直调在用，改为与带切面路径同样处理（引用未持久字节 → 放弃本轮）。
- **恢复 / 只读内存视图**：`install_memory_view` 的行直接成为一个 frozen 段；恢复期 `recover_row` 追加的行照常进 active。
- **冻结时的拷贝**：仍需在 `mu_` 下把 seq ≤ S 的行拷出来（与现状的前缀拷贝同量级）。若要消除，可把 active 改成分块存储、整块移交，这一步不在本设计范围内。
- **视图对象的构造成本**：每次发布拷贝两个小数组（run 指针 ≤ `kMaxRuns`，frozen 段通常 ≤ 2），可忽略。

**对 4.7 的影响。** I3（成对提交）改述为：「读者看到的 runs 与 frozen 恒来自同一个 `OkiView`；active 行经 `frozen_through` 过滤后与该视图不重叠」。陷阱 3 随之消失，但换来一条新的必测项：**读者必须先取 active、后取 view，并做 seq 过滤**——漏掉过滤就退回原来的等 ord 判反。

## 5. 预期收益

### 5.1 写放大（每写入一行平均被重写次数）

| N | F | 现状（全归并） | 分级（K = 1，≈ log₂(N/F)） |
|---|---|---|---|
| 1000 万 | 1M | ~1.3× | ~3.3× |
| 1000 万 | 64K | ~19× | ~7.3× |
| 1 亿 | 1M | ~12× | ~6.6× |
| 1 亿 | 64K | ~190× | ~10.6× |
| 10 亿 | 1M | ~125× | ~10× |
| 10 亿 | 64K | ~1900× | ~14× |

注意第一行：千万级、run 又大的场景下，分级反而比全归并多写。这是对数与线性的交叉点，绝对量都很小（GB 级以下）；如需完全不劣化，可在 N 较小时（例如底座 < 16·F）直接走全归并（4.3 的开关就能表达）。

### 5.2 读放大

常驻 run 数 ≤ log₂(N/F) + 1（且受 `kMaxRuns` 限制）：1 亿 key、F = 64K 时约 12 个，现状 ≤ 9 个。点查每多一个 run 多一次内存 bloom 判定（~1% 误判率才会多一次块读），range 归并多一路游标，影响很小。

### 5.3 空间

墓碑行在非全归并中保留，空间回收比现状慢一些；由 4.3 的墓碑占比触发兜底。

## 7. 测试计划

1. **策略单元测试**：给定 run 大小序列验证选段；模拟 10⁴ 次随机大小 flush，断言 run 数始终 ≤ `kMaxRuns`、每行累计重写次数 ≤ ⌈log₂(N/F_min)⌉ + 常数。
2. **模型对拍**（核心）：随机 put / remove / 同 ord 搬迁 / flush / 后缀归并 / 全归并，与一个内存 map 模型逐 key 对比 `locate`、迭代结果。重点场景：
   - put 在底座、墓碑在小 run，后缀归并不含底座 → key 仍不可见（墓碑必须保留）；
   - 搬迁行与原行分处后缀内外 → 新位置胜出；
   - 归并期间并发 flush / rebuild → 提交放弃或正确拼接。
3. **崩溃**：在「输出 run 已写、manifest 未提交」处中断 → 重开后输出作为孤儿被清理，数据完整。
4. **T-0 专项**：写者持续「追加原始行 → 追加同 ord 搬迁行 → flush」，读者循环构建视图，断言视图里任何 key 的胜出位置都不旧于同视图 run / frozen 段里的同 ord 行；对照组（去掉 seq 过滤）必须能观察到违例，否则测试无分辨力。
5. **并发**：沿用 `AsyncCompactionKeepsReadViewsComplete` / `ReadViewNeverTornByRebuild`，TSAN 下循环跑。
6. **基准**：`OkiState` 直驱，N = 10⁷ / 10⁸，F = 64K / 1M，统计归并重写行数 ÷ flush 行数、归并总耗时、点查 p50/p99、range 吞吐；与 `CompactionPolicy::kFull` 对比。

## 8. 风险与回退

| 风险 | 应对 |
|---|---|
| 非连续归并导致搬迁位置被旧行压过 | 4.1 的后缀约束 + 提交时连续性校验 + 模型对拍专项场景 |
| 后缀归并误丢墓碑导致复活 | 4.4 只有含 R0 才丢；对拍专项场景 |
| run 数在病态 flush 序列下膨胀 | `kMaxRuns` 硬上限 |
| 墓碑长期滞留占空间 | 墓碑占比触发全归并 |
| 小库写放大略升 | 底座较小时直接全归并 |
| 需要回退 | `CompactionPolicy::kFull` 内部开关；盘上格式未变，回退无需迁移 |
| 大归并期间小归并被挡，run 数失控 | 两条归并道（4.5）+ 背压（4.8） |
| 同步归并卡住 reducer / close | 一律后台 + 可取消（4.8） |
| 跨进程读者撞上 sweep | `load` 重读 manifest 重试（4.8） |
| 读视图不成对导致等 ord 判反 | 现有代码靠 `SeqGate` 窗口保证；T-0 之后由 `OkiView` + `frozen_through` 从构造上保证（4.9） |
| T-0 读者漏做 seq 过滤或取数顺序写反 | 封装成唯一入口（视图构建与点查共用一个取数函数）；压力测试 + 对照组 |

## 9. 待定问题

1. K 的默认值（1 还是 2）需要基准数据定；
2. 是否把 K / `kMaxRuns` 暴露成 `CaskOptions`（建议先不暴露，内部常量 + 基准调参）；
3. 墓碑占比阈值（25%）是否需要按 key 规模自适应。
