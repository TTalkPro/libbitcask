# 原子批对并发读者不是整批可见：批内各 key 逐条生效，且按 key 字节序而不是 op 序 —— 下游「头即版本」的乐观并发会静默丢更新

**报的人**：keelson（适配 libbitcask 时压测撞上，根因已确认）；bitcask（Erlang 封装，按同一根因审图层代码，libbitcask 12.0.0 `62dd725`，Linux x64）。
**严重度**：🔴 下游按「一个版本 key 守住一组 key」做的条件写读-改-写会静默丢更新 / 写坏，不报错。读者侧是瞬时读到半个批。

## 症状

不报错。下游看到的是：
- keelson：压测下并发读者读到批的中间状态（同一批里一部分 key 是新值、一部分是旧值），据此算出的写回把别人的修改覆盖掉。
- bitcask：审代码确认图层有同样的读-改-写窗口（见「影响面」）。压测 21 轮（16 / 96 进程并发给同一个 hub 加边）没复现——窗口在两条
  `apply_*` 之间，正常不到一微秒，只有写线程恰好在批中间被抢占才会拉长。

## 位置

- `src/cask/cask.cpp:2554`：`final_ops` 是按 key 字节序排序的 `std::map`，`apply_order` 从它生成 ⇒ **生效顺序 = key 字节序，与调用方的 op 顺序无关**。
- `src/cask/cask.cpp:2823` 起：在 `write_mu_` 内逐条 `authority_->apply_remove` / `apply_put`（`:2826` / `:2835`），每条应用完立刻对读者可见。
- `src/cask/cask.cpp:1780`：`read_doc` 直接 `authority_->state().locate(key)`，不拿 `write_mu_`，也没有批级屏障 ⇒ 能看到半个批。
- 文档：
  - `include/bitcask/txn.hpp:8` 写明「**不提供**隔离性（I）——事务中间态对并发读者可见」，这句是对的；
  - 但 `include/bitcask/cask.hpp:765` 起的 `put_batch_atomic` 注释写「除进程内 all-or-nothing 外」「批内 op 依序 apply」：
    前一句容易被读成「读者看到整批或看不到」，后一句会让下游以为可以靠 op 顺序控制可见顺序。实际两条都不成立。

## 怎么撞上的

典型的下游布局：一个「头」key 记版本 / 目录，若干「块」key 存数据；每次修改都重写头，写回时只对头设 `kOrdEquals`。

```text
写者 W：put_batch_atomic([{put, Head, ..., expect ord=N0}, {put, Chunk, ...}])
        应用顺序（key 字节序）：Head 先（LSN → N），Chunk 后
读者 X：         get(Head) → 新头 N        ← W 已应用 Head
                 get(Chunk) → 旧块          ← W 还没应用 Chunk
X 写回：put_batch_atomic([{put, Head, ..., expect ord=N}, {put, Chunk, 旧块+X 的改动}])
        等 W 放 write_mu_ 后执行；此时 Head 仍是 N ⇒ 条件成立 ⇒ W 写进 Chunk 的内容被覆盖
```

只要头 key 的字节序排在块 key 前面（例如头 key 是块 key 的前缀，bitcask 图层正是这样），同一个顶点就**总是头先生效**。
下游想改成「把头放到批的最后」也没用，因为生效顺序看的是 key，不是 op 顺序。

## 影响面

- 所有用「一个版本 key 守住一组 key」做乐观并发的下游。只对头设条件的读-改-写都会中招；批对读者整批可见是这类设计的前提。
  - bitcask 图层（`graphdb_adj`）命中三处：
    1. 写会话只对改过的头设条件，块不带版本读 ⇒ 丢更新；
    2. 读到「目录有、盘上没有」的块时把它自愈成空块。这一步本来依赖「头条件必然不成立」，遇到半个批会把别人刚建好的块写成空；
    3. `#{consistent => true}` 的一致性读靠读前读后比头的 LSN，挡不住「新头 + 旧块」。
  - keelson：同类（clj-bitcask 图层，布局与 bitcask 图层逐字节相同）。试过的图层补丁挡不住（见「keelson 补充」），已还原，等 libbitcask。
- 读者侧：任何一次读多个 key 的下游（迭代、事务读集、查看工具）都可能看到半个批，只是瞬时不一致。
- 不报错、不留痕迹。写坏之后表现为计数和条目对不上、两端不对称、边 / 条目丢失。

## 建议（下游不替 libbitcask 拍板）

1. **根治：批对读者整批可见。** 例如批级发布屏障：批内各 key 应用到一个暂存视图，最后一步原子切换；或读路径对正在应用的批
   做 seqlock 式重试。点查、迭代、range 至少要保证不会看到半个批。下游各自打补丁（给整个读集加条件）能挡住写坏，
   但每个下游都要知道这件事、都要自己做对。
2. **做不到 1 的话，至少把契约写准**：
   - `put_batch_atomic` 注释写明「对并发读者不是原子的；批内按 key 字节序逐条生效，与 op 顺序无关」，
     删掉或改写「进程内 all-or-nothing」「依序 apply」两句；
   - 写明下游的正确用法：条件要覆盖**整个读集**（每个读过的 key 都要 `kOrdEquals` / `kAbsent`，没改的用 `kCheck`）。
3. **给读者一个校验手段**，并写进文档。只含 `kCheck` 的批在 `write_mu_` 内校验、不写盘（`cask.cpp:2539` 提前返回），
   可以拿来在写锁下校验一组读到的版本是否仍是当前值，给一致性读用（bitcask 打算这样修）。建议把这个用法写成文档承诺，
   或者提供一个专门的 `validate(keys, ords)` 入口（不要求可写句柄）。
4. 回归：
   - 两个线程，一个反复用原子批写「头 + 块」，另一个反复「读头 → 读块 → 带头条件写回」，断言块内容不丢；
   - 读者断言永远读不到半个批（做了 1 之后）。

## keelson 补充（2026-11-20，libbitcask 12.0.0 `62dd725`，Linux x64，经 clj-bitcask FFM）

### 1. 窗口不小：KV 级稳定复现，不需要写线程被抢占

1 个写线程反复 `put_batch_atomic[_cond]`，一批把 `k000 … k00N` 都写成同一个递增数；4 个读线程反复「先读 `k000`、再读 `k00N`」，
后读的那个比先读的旧就算读到半批（2 万批）：

| 每批 key 数 | 带条件 | 读次数 | 读到半批 |
|---|---|---|---|
| 2 | 否 | 155 015 | 3 102（2.0%） |
| 2 | 是（条件挂在批首） | 328 748 | 17 409（5.3%） |
| 8 | 是 | 455 166 | 67 389（14.8%） |
| 8 | 否 | 243 081 | 56 023（23.0%） |

反过来读（先读字节序最后的 key、再读最前的，断言「最后的新 ⇒ 最前的也新」）：4 组共约 164 万次读，0 次违反——与
「生效顺序 = key 字节序」一致。这一组可以直接当建议 4 第二条的回归用例。

### 2. 下游实际写坏成什么样

clj-bitcask `graph-v1-test/concurrent-mixed-ops-keep-invariants`（8 线程加 / 删边 + 2 线程删顶点，12 个顶点，
`adj-inline-max` / `adj-chunk-max` = 128）：

- 失败率：12.0.0 是 8 / 300，11.0.0 是 9 / 300 ⇒ 不是 12.0.0 引入的。
- 静止后全图校验报的种类（1500 轮里 21 轮坏）：两端不对称 11、组计数 ≠ 实际条目数 4、头解不了码 3、块越界 1；另有运行中读头直接报畸形 2 次；别的轮次还见过「目录有、盘上没有」的块。
- 写坏的头的原始字节：`01 0001 | 01 00 00000007 0000000000000001`——内联组、Count = 1、后面没有条目。来路：头说该组已分块，
  读块时块键不在（按空块处理），收尾把它转回内联，计数沿用头里的。

### 3. 只在下游打补丁，试过的两种都不够

- **批内把头排到最后**：没用，失败率不变量级（3000 轮 20 轮坏）。与本文「生效顺序看 key 不看 op」一致：图层的头 key 是块 key 的前缀，头总是先生效。
- **会话读过的每个顶点的头都带条件**（改了的挂在头 op 上，没改的补 `kCheck`）：两端不对称明显变少，但「新头 + 旧块」仍然挡不住——头的条件照样成立。
  要挡住得给**每个读过的块 key** 也带 `kOrdEquals` / `kAbsent`，等于放弃「头即版本」，每次读块都要带 ord、批里多出一串校验。

所以建议 2 里「条件要覆盖整个读集」对这类布局的含义是：头和块都算，不只是各顶点的头。

### 4. 核对过没问题的（缩小范围用）

- 条件写不丢更新：10 线程对 6～12 个 key 做「读 ord → 带条件写回」，条件键放批首或放批尾、前面垫 0～11 条无条件 put / delete，共 700 轮，终值 = 成功提交次数。
- 批与批之间的生效次序 = 提交次序：8 线程，每批 6 条无条件 put / delete + 批尾一条带条件的序号键，500 轮，静止后各 key 正好是最后一批留下的样子。
- 只含 `kCheck` 的批、以及与写 op 混在一批的 `kCheck`：不改被校验 key 的值和 ord，ord 不对时整批作废。

### 5. 文档还有一处

`doc/api-c.md` §10.3（约 1118～1120 行）同样写着「批内 op 依序 apply」，改 `cask.hpp:765` 时一并改。
