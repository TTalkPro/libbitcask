# 数据文件中间一条记录头损坏 + 索引从 data 重建 ⇒ 从损坏处把文件截断，其后已落盘的记录全部静默丢失

**报的人**：bitcask（对照 LatticeDB 的日志恢复做法核对 libbitcask 现状时复现。libbitcask 12.0.3 `d995557`，Linux x64）。
**严重度**：🔴 已 fsync 的数据被静默删除（文件被截断），`open` 成功、不报错、不留日志。触发条件窄（一处位腐恰好落在记录头的长度字段上 +
随后一次从 data 的全量重建），但后果不可逆。

## 症状

不报错。2000 条记录（每条 168 字节）写完、`sync`、`close`，然后把第 1000 条记录的 23 字节头整个改成 `0xFF`：

| 重开方式 | data 文件大小 | 读得到的 key | 第 1000 条 | 第 1500 条 |
|---|---|---|---|---|
| 索引文件都在（`kv.oki.*`） | 336000 → 336000 | 1999 / 2000 | `{error, io_error}` | 正常 |
| 先删掉 `kv.oki.*`（派生缓存，文档说可删，重开从 data 重建） | 336000 → **167832** | **999 / 2000** | `not_found` | **`not_found`** |

第二种情况下 `open` 返回成功，文件被截到损坏处，第 1001～2000 条——全部是 fsync 过的完好记录——从盘上消失。
之后再也恢复不了（字节已经被 `ftruncate` 掉）。

## 位置

- `src/fileops/data_file.cpp:406` `DataFile::fold`：`if (offset + rec_total > total) break;`——记录头里的长度超出文件剩余字节就当成
  「文件尾被 torn write 截断」，停止扫描，`out_last_valid_end` 停在上一条末尾。它分不清「这是没写完的尾巴」还是「中间一条的头坏了」：
  长度字段被改大（本例 `0xFFFFFFFF`）与真正的短尾巴走同一个分支。
- `src/cask/cask_recovery.cpp:505`（全量 fold 的 `fold_one`）与 `:379`（流式恢复的 tail fold）：只要
  `last_valid_end < 文件大小`、句柄可写，就 `truncate_to(last_valid_end)`。**对每个被 fold 的文件都这么做**，不区分它是不是最后一个
  （只有最后一个被写的文件才可能有 torn tail）、也不看被截掉的区间是否早已 fsync。
- 对照：同一个文件里只坏了记录体（CRC 不过）走 `tolerate_crc_errors` 跳过这一条（`data_file.cpp:418`），不会截断——
  所以「坏一个字节丢一条」与「坏一个字节丢半个文件」的差别只取决于那个字节落在头里还是体里。
- 索引在时不触发：流式恢复只 fold manifest 水位之后的 tail（`cask_recovery.cpp:331`），水位之内的坏记录到 `get` 时才报错（上表第一行）。
  顺带：那里报的是 `io_error` 而不是 `bad_crc`，下游分不出是磁盘读失败还是这条记录坏了。

## 怎么撞上的

```erlang
R = bitcask:open(Dir, [read_write]),
V = binary:copy(<<"v">>, 128),
[ok = bitcask:put(R, <<"k", I:64>>, V) || I <- lists:seq(1, 2000)],
ok = bitcask:sync(R), ok = bitcask:close(R),
[Data] = filelib:wildcard(Dir ++ "/*.bitcask.data"),
{ok, Fd} = file:open(Data, [read, write, binary, raw]),
ok = file:pwrite(Fd, 999 * 168, binary:copy(<<16#FF>>, 23)),    %% 第 1000 条的记录头
ok = file:close(Fd),
[file:delete(F) || F <- filelib:wildcard(Dir ++ "/kv.oki.*")],  %% 触发从 data 全量重建
R2 = bitcask:open(Dir, [read_write]),                            %% 成功；data 文件 336000 → 167832 字节
not_found = bitcask:get(R2, <<"k", 1500:64>>).
```

脚本在开发机 `/tmp/gprof/trunc.escript`（bitcask 仓库根目录用 `escript` 跑，两种重开方式各一遍）。

会走全量 fold 的场合不止「手工删索引」：OKI manifest 缺失 / 损坏、跨版本升级要求重建、运行期受控重建之后的下一次打开、
manifest 不认识的文件（快照后新建的文件、merge 产物，`wm_of` 返回 0）。

## 影响面

- 任何可写打开。只读 / merge_only 句柄不截断。
- 损坏来源不限于磁盘位腐：别的进程误写、拷贝中断后续传、文件系统故障后 `fsck` 填零，都可能让某条记录头的长度字段变成大数。
- 不报错、不留痕迹。下游看到的是「一批 key 不见了」，而它们明明 `sync` 过。因为截断是物理的，事后拿不回来；
  而如果不截断，这些记录本来是完好的，只丢那一条。

## 建议（下游不替 libbitcask 拍板）

LatticeDB 的做法可以参考：它在每个日志帧里记「上一次 fsync 时已有多少帧」，恢复时已同步范围内的坏帧判为损坏并拒绝打开，
范围之外的才当成没写完的尾巴截掉。libbitcask 手里已经有等价的信息，不需要改盘上格式：

1. **只有「最后一个被写的文件」的尾巴才允许按 torn write 截断。** 更早的文件（已 roll / 已封口）不可能有没写完的尾巴，
   在它们中间停下来 ⇒ 损坏，不截断。
2. **已知持久的区间不截断。** manifest 里有各文件的 data 水位（`manifest_data_wms`），写者也有持久水位；
   `last_valid_end` 落在已知持久的字节之前 ⇒ 损坏。
3. **停下来之后往后探一下再决定。** 真正的 torn tail 之后没有完好的记录；如果在停下的位置之后还能重新同步上
   （例如按记录头的固定特征 + CRC 向后扫描找到下一条完好记录），那就不是尾巴——跳过坏区间继续，至少不截断。
4. 判为损坏时的处置由调用方选：缺省拒开并报出文件名与偏移（`kBadCrc` / 新的损坏码）；或提供一个「抢救」开关——
   跳过坏区间、保留其后的记录、记 warning，但**永不 `ftruncate`**。
5. 顺带：水位之内的坏记录在 `get` 时报 `kBadCrc`，不要并进 `kIo`。
6. 回归：本例（坏头在中间 + 删索引重开）断言文件大小不变、其后的 key 都在或 `open` 明确报损坏；
   真正的 torn tail（最后一个文件末尾半条记录）仍按现在的语义截断。

## 回没回
