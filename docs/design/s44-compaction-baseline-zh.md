# S44 OKI 分级归并：基线与对比报告

日期：2026-11-16 · 关联：`designs/oki-size-tiered-compaction-design-zh.md`、`TASK.md` S44-0 / S44-6

## 1. 测量方法

- 工具：`bench/oki_compaction_bench.cpp`（`bitcask_oki_compaction_bench <dir> <N> <F> <full|tiered> [K]`），
  `OkiState` 直驱，不经 Cask / data 文件。
- 负载：N 次写入，key 从 `[0, N)` 均匀随机抽取（含覆盖写，最终约 63% 为不同 key——稳态服务负载），
  每 F 行 flush 一次；写完后 `wait_compaction()`。
- 指标：
  - **写放大** = 归并输出行数 ÷ flush 写入行数（每写入一行平均被归并重写几次；flush 本身不计）；
  - 归并累计耗时（后台线程上的耗时总和，可与写入重叠）、总墙钟；
  - 最终常驻 run 数；
  - 点查 p50 / p99：10 万次随机命中 key，先预热 2 万次；块缓存 256MB 默认值。
- 「现状」= `CompactionMode::kFull`，选段规则与旧全归并逐字等价（run 数 > 8 即全量重写）。差别：旧实现
  在非阈值提交点同步归并、阈值 flush 交后台；本基准里两者都后台执行，**写放大口径完全一致，耗时口径
  不完全一致**（旧实现同步归并会进一步拉长写入墙钟）。
- 机器：192.168.3.13（8 核、23GB 内存、SATA/SSD 系统盘，数据放家目录分区而非 tmpfs）。Release + LTO。
- 每组只跑一次。**p99 噪声明显**（见 §3），结论以写放大和归并耗时为主。

- 背压：10⁸ / 64K 分级触发 44 次、全归并在 10⁷ / 64K 触发 8 次（全归并模式下没有年轻道，大归并期间

## 3. 结论

- **写放大**：小库（10⁷、run 大）持平；10⁷ / 64K 降 46%；10⁸ / 1M 降 41%；10⁸ / 64K 从约 62 降到
  4.18（约 15 倍，全归并侧为估算）。归并累计耗时同比下降 41%～54%。
- **读放大**：常驻 run 数从 1～2 个增加到 4～8 个。点查 p50 上升约 5%～35%；p99 在 10⁸ 上从 8.0µs
  升到 18～19µs（约 2.3 倍）。但 p99 噪声大：同为单 run 的全归并在 10⁷ / 64K 上 p99 是 18.5µs，
  10⁸ / 1M 上却是 8.0µs，单次测量不足以给出可靠的 p99 结论。
- **K 的选择**：K=2 在 10⁷ / 64K 上写放大 4.04（K=1 为 2.83），只少 1 个 run，点查没有改善。保持 K=1。

## 3a. 点查门限（2026-11-16 写于修复与复测之前）

首轮测量时没有先行写明门限（偏差，见 §4）。在着手修复 p99 回退、重新测量**之前**，先固定门限如下，
复测结果按此判定，不再事后调整：

- 场景：N = 10⁸、F = 1M，同一台机器同一时段，全归并（`kFull`）与分级（`kTiered`, K=1）交替各跑 3 次，
  每组指标取 3 次的中位数；测量期间机器上不跑其它测试。
- 门限：分级 / 全归并 的点查 **p99 ≤ 1.5 倍**、**p50 ≤ 1.3 倍**。
- 附带记录（不设门限）：N = 10⁸、F = 64K 分级的 p50 / p99，与上面全归并的中位数对比。

## 3b. 复测（按 §3a 协议）

**修复**：首轮 p99 回退的主因是 bloom 假阳性叠加——分级下常驻 4～8 个 run，未命中的 run 各按约 0.8%
（10 bits / 7 哈希）的概率多读一个块，约 3%～6% 的点查多一次块读，恰好把 p99 推到「两次块读」。新 run
改为 16 bits / 11 哈希（FP ≈ 0.05%）。位数与哈希数写在 run 文件里、reader 按文件读取，旧 run / 旧版本
reader 不受影响；代价是 bloom 常驻内存 +60%（1 亿行约 125MB → 200MB）。

**结果**（10⁸ 行，F = 1M，交替各 3 次；测量期间机器上无其它测试）：

|---|---|---|---|---|---|---|---|---|
| 1 | 全归并 | 3.79 | 168.6s | 199.6s | 1 | 5.37 | 11.86 | 0.632 |
| 1 | 分级 | 2.24 | 107.0s | 154.8s | 5 | 5.95 | 11.87 | 0.633 |
| 2 | 全归并 | 3.80 | 161.0s | 191.9s | 1 | 5.19 | 10.08 | 0.632 |
| 2 | 分级 | 2.24 | 104.9s | 154.2s | 5 | 5.96 | 10.94 | 0.633 |
| 3 | 全归并 | 3.82 | 209.5s | 240.5s | 1 | 5.93 | 14.40 | 0.632 |
| 3 | 分级 | 2.24 | 118.4s | 169.5s | 5 | 6.73 | 15.29 | 0.633 |
| **中位数** | 全归并 | 3.80 | 168.6s | 199.6s | 1 | **5.37** | **11.86** | — |

- 判定：p99 比值 11.87 / 11.86 = **1.00 ≤ 1.5**，p50 比值 5.96 / 5.37 = **1.11 ≤ 1.3**——**达标**。
- 「每次点查块读」两种策略几乎相同（0.633 vs 0.632；约 37% 的查询 key 不存在，被 bloom 直接拒绝），
  印证多余块读已被消除。
- 附带记录（无门限）：10⁸ 行、F = 64K 分级：写放大 3.92、6 个 run、p50 7.59µs、p99 24.32µs、每次点查块读
  0.634——约为上表全归并中位数的 1.4 倍（p50）/ 2.1 倍（p99）。块读数相同，额外耗时推测来自逐 run 的
  bloom 探测（每个 run 11 次随机内存访问、bloom 总量约 200MB，缓存未命中随 run 数线性增长），**未单独
  验证**。若要进一步压低，可改成缓存行局部（blocked）bloom，属 run 格式演进，另行立项。

## 3c. 第二批门限（2026-11-16 写于补测之前）

§3b 中 10⁸ / F=64K 的 p99 只记录未设门限，range 吞吐与墓碑占用空间未测。补测**之前**先固定以下门限，
结果按此判定，不再事后调整。

**同数据对比法**：每次运行先以分级策略写完并测量，再在**同一份数据**上强制全归并成单个 run 后重测。
两次测量的数据集、key 分布与页缓存状态相同，只有 run 数不同——隔离「run 数」这一个变量。

| # | 场景 | 指标 | 门限 |
|---|---|---|---|
| G1 | 10⁸ 行、F = 64K，3 次取中位数 | 点查 p99（分级 / 同数据全归并） | ≤ 1.5× |
| G2 | 同上 | 点查 p50（分级 / 同数据全归并） | ≤ 1.3× |
| G3 | 同上 | 全量迭代吞吐（行/秒，分级 / 同数据全归并） | ≥ 0.7× |
| G4 | 同上 | 短区间扫描（随机起点取 100 行）p99 | ≤ 1.5× |

## 3d. 第二批结果（按 §3c 判定）

### 过程中发现并修复的问题

补测暴露了选段策略在两条归并道并发下的两个缺陷，均已修复（`oki_compaction_policy.cpp`）：

1. **硬上限驱动年轻道**：主道重写大 run 时其输入仍在册，总 run 数必然越过上限；年轻道也被上限驱动后，
   每来一次 flush 都把自己积累的全部 run 重写一遍。实测写放大 28、墙钟 540s。→ 硬上限只作用于主道。
2. **「新而大」倒挂**：年轻道的选段受 floor 截断而非大小条件，可能产出比其前面的 run 更大的 run；几何
   遍历从此在它处停下，其前更小的老 run 永远并不进去，叠加硬上限后每次 flush 都重写那个大 run（实测
   底座之前留着 5 个几十 MB 的老 run、其后是 1.2GB 的 run）。→ 主道发现明显倒挂（老 run × 2 < 某更新
   run）时从倒挂点起修复性归并；被硬上限扩大后缀后继续按几何规则吸收。

另外：`max_runs` 默认 24 → 6（flush 背压阈值另设，默认 2 × max_runs，避免主道大归并期间卡住写入）；
归并游标改为堆 + 下沉提前退出 + 前 8 字节整数比较（全量迭代 +15%）；区间起点定位块走块缓存
（`seek_cached`）；多 run 点查哈希只算一次。尝试过的 bloom 预取实测无可分辨收益，已撤回。
测量方法补充：每次测量前 `sync()` + 静置 3 秒（同一布局紧跟大量写盘之后测，p99 实测被抬高约 1.7 倍）。

### G1–G4：10⁸ 行、F = 64K，分级（6 个 run）vs 同数据全归并（1 个 run），3 次中位数

| # | 指标 | 分级 | 同数据全归并 | 比值 | 门限 | 判定 |
|---|---|---|---|---|---|---|
| G1 | 点查 p99 | 16.87µs | 10.51µs | 1.61× | ≤ 1.5× | **未达标** |
| G2 | 点查 p50 | 6.10µs | 4.58µs | 1.33× | ≤ 1.3× | **未达标** |
| G3 | 全量迭代 | 8.92M 行/s | 22.12M 行/s | 0.40× | ≥ 0.7× | **未达标** |
| G4 | 短区间（100 行）p99 | 129.8µs | 28.9µs | 4.5× | ≤ 1.5× | **未达标** |

- 数据来自最终选段规则 + `max_runs = 6` 的一批（三次原始值：p99 135.38 / 16.87 / 15.13 对 9.84 / 10.51 / 13.45；
  p50 5.99 / 6.39 / 6.10 对 4.76 / 4.51 / 4.58；迭代 8.92 / 8.92 / 8.53M 对 22.05 / 22.59 / 22.12M；区间 p99
  172.4 / 124.2 / 129.8 对 25.3 / 38.4 / 28.9）。此后的游标优化把同一布局的全量迭代提到约 10.6M 行/s（≈0.48×，
  新进程复测，未重跑同数据三次）；点查路径此后只改了「哈希只算一次」。
- 定位实验：把分级布局保留在盘上、在全新进程里只加载并测量，p50 约 6.1µs、p99 13～19µs，与写入后立即测
  一致——额外开销来自布局本身，不是写入阶段的进程状态。perf：点查里块内顺序解码与 key 比较两种布局都付；
  多 run 额外付的是每个不命中 run 的 bloom 探测（十几到几十 MB 的数组，缓存与 TLB 未命中）。区间扫描额外
  付的是逐 run 定位（块内顺序解码）与多路归并，且分级布局的源行数多约 32%（旧版本与墓碑）。
- **结构性冲突**：在本场景（约 1526 次 64K flush）减少 run 数会让写放大急剧上升（选段模拟：上限 6 → 6.35，
  5 → 10.5，4 → 24.2；全归并约 62）。上限降到 5 以下即违反「写放大下降一个数量级」的验收项，而 G1–G4 要求的
  读性能接近单 run。也就是说，**在当前 run 格式下，G1–G4 与写放大验收项不能同时满足**。
- 实测 `max_runs` 24 → 6 对读路径没有可分辨的改善（9 个 run 时 p99 1.60×、迭代 0.38×；6 个 run 时 1.61×、
  0.40×），写放大约 +25%（3.9 → 4.9）。保留 6 的理由是给 run 数 / fd / 内存设上界，且删除负载下空间放大在门限内。

## 3e. 测量方法修正（2026-11-16，写于重测之前）

**发现**：在基准里加了点查分解测量（用公开接口复刻 locate 的 run 段：依次查各 run 的 bloom 直到首个
命中，再在命中 run 上 find），10⁸ / 64K 保留在盘上的同一份数据：

| 布局 | bloom p50 / p99 | find p50 / p99 | 合计 p99 |
|---|---|---|---|
| 分级 6 run（新进程，3 次） | 0.9～1.0 / 1.9～3.3µs | 8.6～9.7 / 157～234µs | 158～236µs |
| 全归并 1 run（刚归并完） | 0.37 / 0.82µs | 4.9 / 115µs | 116µs |
| 全归并 1 run（新进程） | 0.30 / 0.52µs | 5.4 / 10.65µs | 11.26µs |

点查 p99 尾部几乎全部在 find 段，量级（100～250µs）是读盘：测量时 run 文件有一部分不在页缓存里。全归并
刚写完的文件整份驻留；分级布局里写得早的 run 在测试期间约 10GB 写入压力下被挤出一部分。本机是共享
机器（测量期间另有 Java / Jinshu / Chrome 负载，15 分钟平均负载到过 14），驻留程度还会随外部负载漂移——
这也解释了 §3d 里的 100µs 以上尖刺。**§3c / §3d 的 G1 / G2 因此混入了「文件在页缓存中的驻留程度」这一
与 run 结构无关的变量。** 真正由多 run 结构带来的是 bloom 段（p50 约 +0.6µs）。

**修正**：此后每次测量前，除 `sync()` + 静置 3 秒外，再把目录内全部 run 文件顺序读一遍使其驻留页缓存，
两个阶段同样处理——比较「索引常驻页缓存」的稳态服务场景。§3c 的门限、场景、3 次取中位数的协议**不变**；
§3d 的旧数据保留不删。页缓存不足时（索引放不进内存），分级布局多出的约 32% 字节会让读盘更多，这一点
记为已知取舍，不在本门限内。
