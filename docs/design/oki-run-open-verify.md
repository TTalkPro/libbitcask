## 1. TODO 原条目与复核结论

原条目：「OKI 大 run 惰性 / 分块校验：`oki_run.hpp:265` 自注『后续优化』仍在。BM25 段
同形态 6.6.0 已修（分块定位读），先例与代码模板现成，工作量短。」

复核后**前提不成立**：

| TODO 的判断 | 实际情况 |
|---|---|
| 与 BM25 段「同形态」 | ❌ 6.6.0 修的 BM25 问题是**内存**：逐节 CRC 直接扫 mmap 映射，触碰的页全部算进进程工作集（报账库 104 MB）。OKI run 的整文件 CRC **从一开始就是 64 KB 分块 `pread`**（`oki_run.cpp` `OkiRunReader::open`），不经 mmap，**没有**工作集问题 |
| 先例可直接套用 | ❌ BM25 的修法（mmap 扫描 → 分块定位读）OKI 早已是后者，无可套用 |
| 工作量短 | ❌ 剩下的问题是开库 **I/O 时间**；要做到真正惰性，run 格式只有一个整文件 CRC，必须改格式（见 §4） |

所以 D2 真正的问题只剩：**大 run 在开库时被整读一遍校验，耗时与 run 总大小成正比。**

## 2. 现状

### 2.1 run 格式（`include/bitcask/oki_run.hpp` 头注释）

```
header 8B | 数据块区（~4 KiB/块，块内前缀差分）| 稀疏索引区 | (v2) bloom 区 | trailer
trailer: [entry_count][index_off][(v2) bloom_off][crc u32][magic "BCOE"]
CRC 覆盖 [0, size-8)——整文件只有这一个 CRC
```

### 2.2 何时校验

- `OkiState::load`（开库）：manifest 里的**每个** run 都 `OkiRunReader::open`，
  open 内整文件 CRC；**任一 run 失败 → 整个 OKI 弃用，走重建**（派生缓存语义）。
- 刚写完的 run（flush / 归并 / 重建）在提交 manifest 前也 open 一次；此时文件在
  页缓存里，校验便宜。

### 2.3 为什么校验不能随便省：get 路径不核对 key

Level B 下点查走 `keydir_->locate()`：缓存 miss 时从 run 的块里取出位置
（file_id / offset / total_sz / tstamp）。随后 `Cask::get`（`cask.cpp` 约 1612 行起）
按这个位置读 data 记录，**只校验记录自身的 CRC，不比对记录里的 key 是否等于
请求的 key**。

因此，如果某个 run 块损坏、而损坏恰好把位置改成**另一条完好记录**的位置：

- 记录 CRC 通过；
- `get(k1)` **静默返回 k2 的值**。

此外 flags 字节的 tomb 位翻转会让存在的 key 返回 NotFound，ord 字段损坏会影响
版本仲裁——这些都不会被 data 记录的 CRC 发现。**今天这些情况全靠开库时的整文件
CRC 在源头拦住。**

## 3. 待量化（实施前第 0 步）

TODO 未给出实测。需要先回答「开库这一遍到底多慢」，再决定值不值得改格式：

- 测量对象：Level B 库在 10M / 100M key 下的 run 总大小；冷缓存（`echo 3 > drop_caches`）
  与热缓存两种开库耗时中，run 校验所占的份额；

  0.5–1 s，机械盘 / 网络盘可到 10 s 级。桌面场景（keel / coxswain）受影响最大。

若实测开库校验占比很小，本条可直接关闭。

## 4. 方案

### 方案 A：保持现状（整文件 eager CRC）

- 安全性最高，零改动。
- 开库 I/O = run 总大小。

### 方案 B：开关跳过整文件 CRC

照 6.6.0 `segment_verify_crc` 的先例，给 OKI 加一个开关：关闭时开库只校验 header /
trailer / 稀疏索引 / bloom（这些是开库必须读的小区域），数据块不校验。

- 改动小，无格式变化。
- **风险高于 BM25 段的同名开关**：BM25 段损坏最多影响检索排序或命中；OKI 块损坏会让
  `get` **静默返回别的 key 的值**（§2.3）。
- 若采用，必须同时做 §5 的「get 核对 key」加固，否则不建议提供此开关。
- 即便加了 key 核对，tomb 位 / ord 损坏仍无法被发现。

### 方案 C：run v3，每块独立 CRC，首次读取时校验（推荐）

**格式**：稀疏索引的每个条目追加该块的 CRC32（`{klen, 块首 key, block_off, block_crc u32}`）。
索引本身、bloom 仍由一个覆盖「索引 + bloom + trailer 前部」的 CRC 保护，开库时校验
（小区域）。

**校验挂点**：`OkiRunReader::Cursor::load_block`（`oki_run.cpp` 约 501 行）有两条
加载路径，都在 loader 里 pread 一个块：

- 走块缓存（`OkiBlockCache::get_or_load` 的 loader）：pread 后**先校验 CRC 再入缓存**；
  之后的缓存命中不再校验，也就不需要额外的「已校验」位图；
- 直读路径：每次 pread 后校验（该路径主要是归并 / 重建的顺序扫描，块只读一次）。

校验失败返回 `OkiError::kCorrupt`，与今天「run 坏 → 弃用 OKI 重建」同一处理，只是从
开库时刻推迟到第一次碰到坏块时。

**兼容**：

- run 是**派生缓存**，改格式不需要 flag-day：v3 读端同时支持 v1 / v2（后两者仍 eager
  整文件 CRC）；写端新写 v3；旧 run 在下次归并 / 重建时自然换成 v3。
- manifest v2+ 条目已带 `format_ver`，可直接区分。
- 旧二进制遇到 v3 run：读端「未来版本 → kCorrupt → 弃用重建」（`OkiRunReader::open` 已有
  此分支），**退化为重建，不会读错**。需要在 CHANGELOG 写明降级会触发一次重建。

**代价**：

- 索引每块多 4 字节，4 KiB 块下约 0.1% 空间；
- 每次缓存 miss 多一次对 4 KiB 的 CRC（硬件指令，相对 pread 可忽略）；
- 运行期才发现坏块时，需要在线弃用 OKI 并触发重建。今天坏 run 只会在开库时出现，
  运行期弃用路径要新增并测试（可复用 `OkiState` 未加载态的降级逻辑）。

### 方案 D：开库后台异步校验

开库立即返回，后台线程跑整文件 CRC；失败则弃用 OKI。

- 无格式变化。
- 校验完成前的读取使用未校验数据，风险窗口等同方案 B；
- 需要处理「校验中途 OKI 已被归并替换」等并发状态。
- 不推荐：复杂度接近方案 C，安全性不如方案 C。

## 5. 独立于方案的加固：get 核对 key（建议无论选哪个都做）

`Cask::get` 读到 data 记录后，比对记录里的 key 与请求 key；不等时视为索引损坏
（返回 `kBadCrc` 或专门的错误，并在 Level B 下触发 OKI 弃用重建），而不是返回别人的值。

- 成本：每次 get 一次 key 长度的 memcmp，记录已在缓冲里；
- 覆盖的不只是 OKI 损坏：任何原因导致的定位错误（如 merge 搬迁竞态的未知 bug）都会
  从「静默错值」变成「可见错误」；
- 需确认零拷贝 mmap 路径（`read_mmap`）也能拿到 key 做比对。

## 6. 推荐

1. **先做 §3 的量化**。开库校验占比不显著则关闭本条（保持方案 A）。
2. 若显著：**方案 C**，并同时做 **§5 的 key 核对**。
3. 不推荐单独提供方案 B 的开关；若下游确实需要「今天就能跳过」，只在 §5 落地之后提供，
   并在 API 文档里写明 tomb / ord 损坏不可检测。
