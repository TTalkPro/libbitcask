## 1. 需要动手的问题

### P1 — `write_mu_` 持锁期间可能阻塞，写吞吐悬崖风险 🟡

**位置**：7 个 `write_mu_` 获取点（`cask.cpp:1203/1666/1721/1876/1930/2253/2273`），
全部用 `std::lock_guard`（RAII，持锁到函数尾）。

#### 设计前提 vs 实现的错位

[`thread-safety.md`](thread-safety.md) §4 否决细粒度写并发的核心理由是"单 append log
写是 IO-bound，串行化不是瓶颈"（锁 ~20ns ≪ pwrite/fsync µs–ms）。这个论证假设临界区
**有界**。但实际临界区包含三个**无界或长尾**阻塞点，使该论证失效：

- **H1**：IndexPool `queue_.push()` 背压 —— **无界**（取决于索引 worker 消费速度）
- **H2**：`maybe_group_commit` → `fdatasync` —— 有界（10–100ms）
- **H3**：`backup()` 文件系统循环 —— 有界但可达秒级

关键证据：[`async-index-pipeline.md`](async-index-pipeline.md)（Jun 23）**早于**
`write_mu_`（Jun 25 S11-W1）。两个 feature 的交互从未被任何设计文档分析。
`cask.cpp:860-861` 注释明确写"push 阻塞写线程"，但没人把它和"`write_mu_` 此时被持有"
连起来看。

#### H1 — IndexPool 背压（最严重，无界延迟，未文档化）🔴→🟡

5 个写路径（`put`/`put_batch`/`remove`/`put_doc`/`close_write_file`）持 `write_mu_` 调
`submit_index_task()` → `index_pool_->submit()` → `tbb::concurrent_bounded_queue::push()`
（cap=10240）。队列满时 push 阻塞，`write_mu_` 不释放 → 所有其他写者全队冻结。

**触发条件**：慢分析器（Jieba 比 Ngram 慢 3×）、大文档（高维向量 + 长文本）、merge 抢
CPU、批量导入（生产 > 消费）。

**为什么是 bug 形状而非纯设计取舍**：延迟无上界（不像 fsync 有物理上界）、未被任何设计
文档分析、影响**单写线程**（`thread-safety.md` 的多写吞吐论证"分片多 Cask"不适用此场景）。

**可修复性：高**。代码库已有解耦先例（`thread_pool.hpp:559`，reducer 释 `reorder_mu_`
调 `reduce_fn` 后重新获取）。reorder buffer 保证 ord 序正确（`async-index-pipeline.md`：
"本就支持任意到达序按 ord apply"）。数据在释锁点前已持久化（pwrite + keydir put 完成），
索引任务只是内存优化（可从 data fold 重建）。

**修法**：`submit_index_task` 移出 `write_mu_` 临界区。`lock_guard` → `unique_lock`，
keydir put 后 `unlock()`，submit 后 `lock()` 回来做 `maybe_group_commit`。

**✅ 已修复（2026-07-03）**，实际实现与上述草案有两点偏差（均为规避复审发现的隐患）：

1. **不做 unlock→relock**：`maybe_group_commit` 留在锁内（结果捕获、不早退），Add/Delete
   在释锁后提交。relock 方案有"relock 后 active 文件可能已被并发写者 roll，组提交 fsync
   错文件"的世界变化隐患；组提交前置则完全绕开。gc 失败时 Add 仍先提交（ord 必须被真
   任务覆盖），错误随后返回——与旧序（先 submit 后 group_commit）对外语义一致。
2. **新增 `WriteOpGate`（`writes_in_flight_` 计数）**：`close()` 不持 `write_mu_`，锁外
   submit 读 `index_pool_`/`index_lane_` 与 close 的 `unregister_lib` + 指针清空存在
   放大的竞态窗口。写路径全程持 gate（覆盖锁外提交尾段），close 置 `closed_` 后等 gate
   归零再拆资源——违约的并发 close 从 UAF 收敛为阻塞等待。
   `put_batch` 特殊处理：锁内收集 {守卫槽位, 定位记录}，锁外逐条构造提交；中途失败先
   冲刷已收集的 Add（keydir 已收录的条目必须由 Add 覆盖，不能落给守卫的 Skip）。
   回归测试：`CaskDocValueTest.H1CloseConvergesWithInflightWriters`（TSan 验证 gate 同步）。

#### H2 — fsync 持锁（有界，部分已知取舍）🟢

`maybe_group_commit`（`cask.cpp:1160-1172`）在 `sync_every_n` 阈值到达时调 `fdatasync`。
`sync()` 整个函数就是 fsync。

**已有缓解**：`sync_every_n` 批提交摊薄成本；`o_sync` 模式下 `maybe_group_commit` 是
no-op；hint 不 fsync（可从 data 重建）。

**判断**：`thread-safety.md` 部分承认的取舍。`sync()` 是用户显式请求的持久化屏障，可接受。
周期性 fsync 在合理 `sync_every_n` 配置下可接受。彻底解耦需异步 fsync 线程（大重构，
ROI 低）。**不是 bug，是可调优设计点**。

#### H3 — backup 持锁（有界但可达秒级，未文档化）🟢

`backup()`（`cask.cpp:2273-2337`）持锁跨 `create_directories` + 循环 `create_hard_link`/
`copy_file` + `scan_dir`。跨设备 copy 大文件可达秒级。

**特殊性**：backup 需一致性快照，持锁 intentional。但"持锁做整个 copy"过于保守。

**可修复性：中**。snapshot-and-release 模式：持锁 → `maybe_group_commit(force)` + finalize
hint（触发 roll，sealed 旧文件）→ 记录 sealed 文件列表 → **释锁** → 对 sealed 文件做
copy（append-only，不再变化）→ 完成。

#### 修复优先级

| 子问题 | 严重度 | 修复价值 | 状态 |
|---|---|---|---|
| **H1** IndexPool 背压 | 🟡 | 高（影响单写线程，无界延迟）| ✅ 已修复（2026-07-03）|
| H2 fsync | 🟢 | 低（已有批提交缓解，取舍可接受）| 文档化，暂不动 |
| H3 backup | 🟢 | 低（低频管理操作）| 文档化，暂不动 |

#### 非 bug 的确认

非死锁：IndexPool worker 不会再入 Cask 抢 `write_mu_`（reducer 只调 `search_` 方法，
Explore agent 已确认无 callback 持锁路径）。锁序干净：`write_mu_`（最外）→
`read_cache_mu_` / keydir，无反向依赖。`write_mu_` 是 `std::mutex`（非 recursive），
当前代码无递归获取（未来若有会死锁，需注意）。

### P2 — `BM_Inverted_FuzzyHot` 单查询回归 39% 🟡

**位置**
- `src/bm25/inverted.cpp` `search_fuzzy` 函数体（~line 1779）
- 引入 commit：`4d9a527`（"perf(S13): P8 中批 6/14 — fuzzy 并行"）

**机制**

| Benchmark | 旧值（7c429a2）| 新值（9d0657f）| 变化 |
|---|---|---|---|
| `BM_Inverted_FuzzyHot`（"hoot" d=1）| 595 us / 168 M items/s | 986 us / 102 M/s | **−39%** |
| `BM_Inverted_FuzzyVocabScan`（"term12345" d=2）| 6115 us / 32.7 M/s | 1812 us / 110 M/s | **+238%** |

`search_fuzzy` 从串行 `for (auto& shard : shards_)` 改为
`tbb::parallel_reduce(tbb::blocked_range<std::size_t>(0, kShardCount=64), ...)`。

- **冷词全词表扫描**（FuzzyVocabScan）：64 分片吃满并行收益，3.4× 加速。
- **热词单 shard 命中**（FuzzyHot）：白付 TBB task spawn + vector reduction 协调成本，
  单查询延迟 +39%。

**判断**
取舍本身合理（batch 收益 >> 单查询损失），但**取舍不彻底**：单查询 +
`max_edit_distance ≤ 2` 的明显热路径场景没有 fast-path 旁路。

**建议**
在 `parallel_reduce` 前加判断：
```cpp
if (query_terms.size() == 1 && max_edit_distance <= 2) {
    // 串行 fast-path：单热词场景避免 TBB 协调成本
    ... 原串行循环 ...
    return tps;
}
// 否则走 parallel_reduce
```
预计恢复 ~350 us（≈ 旧水平），对批量场景零影响。

## 2. 防御性加固

### P3 — HNSW `copy_neighbors` production 构建形式 UB 🟢

**位置**：`src/vector/hnsw.cpp:548-549`

**问题**
production 构建用 `std::memcpy` 读 adj 数据，writer 侧用 `std::atomic_ref` relaxed 写。
C++ 内存模型下 atomic-vs-non-atomic 同地址访问是 data race → **形式 UB**，
即使 seqlock 复读检测会丢弃 torn 结果。

**为什么不是真 bug**
- TSan 构建正确切到逐字 `atomic_ref`（`hnsw.cpp:535-538` 分支），测试设施健全
- x86_64 对齐 `uint32_t` 硬件保证 word-atomicity，实测安全
- 注释明确承认此取舍（单线程 HNSW 查询 +17%）
- README 限定 GCC 13+/Clang 17+ x86_64，无 word-tearing 架构

**建议**（低成本防御）
在 `copy_neighbors` 的 memcpy 分支加 `static_assert`（仅 x86_64/ARM64 允许），防止未来
移植到 word-tearing 架构时静默继承 UB。

### P4 — `rebuild_hnsw` / `clone_live` 与并发读者无运行时测试 🟢

**位置**：`tests/hnsw_test.cpp`

**问题**
Oracle 推理确认 `clone_live` 在"单写者"不变量下安全（`clone_live` 即写者，不与
`insert` 并发；`search_layer.hpp:506-508` 文档此约束）。但：

- `BM_Hnsw_SearchConcurrent`（`bench/hnsw_bench.cpp:113-133`）**纯只读**
  （`shared_graph(n)` 预构建），名不副实 —— 只测 reader 可扩展性 / hub 缓存乒乓，
  无法抓任何 reader-vs-writer 竞态。
- `Hnsw.ConcurrentReadersWithSingleWriter`（`hnsw_test.cpp:431`）覆盖了 insert 时的
  seqlock + publish 点（OK）。
- **但无任何测试**在读者活跃时调 `rebuild_hnsw()` —— clone_live 的快照一致性纯靠代码
  审查背书。

**建议**
加一个 mirror 测试：writer 线程交替 `insert` 与 `rebuild_hnsw`，读者并发 `search`，
闭这条唯一未验证的 publish 路径。预计 < 1 小时工作量。

**额外约束加固**
`hnsw.cpp:848-849` 的 `writer_active_` 仅 debug `assert`。若 IndexPool 将来重架构为
多 reducer 共享一个 graph，`clone_live` 与 seqlock 写互斥都会**静默崩溃**。建议在
`search_layer.hpp` 的 `hnsw_` 成员附近显眼位置标注此单写者不变量。

### P5 — `write_meta` 用 in-place `trunc`，非 atomic rename 🟢

**位置**：`src/cask/meta_file.cpp:114`

**问题**
`std::ofstream f(path, std::ios::trunc)` 先破坏旧文件再写新内容。崩溃在 trunc 后、
写前 → meta 为空 → 引擎无法 open（数据文件完好，**降级而非数据丢失**）。

**对比**：同 PR 的 `FieldSchema::upgrade_legacy_to_new_`（`include/bitcask/field_schema.hpp:229-249`）
正确用了 `temp → fsync → rename` 的 crash-safe 替换。

**为什么严重度低**
`write_meta` 仅在两个场景调用：
- `cask.cpp:725`（`!meta_exists`，首次建库）
- `cask.cpp:441`（离线 KV→Index `upgrade`）

**运行时不调**（merge / put / close 都不碰）。这是 v2 就有的遗留问题，CRC commit 没引入
也没声称解决。但**若将来加运行时 meta 重写**（如配置热变更）就会变成真问题。

**建议**：纳入下次格式相关清理批次，改成 `temp → fsync → rename`，与 FieldSchema 对齐。

## 4. 已验证为 SOLID 的修复（无需动作）

下列修复经 Oracle / Explore 深度评审确认正确且完整，记录在此供后续审查参考。

### ✅ S13-F1 — merge 重定位条件 CAS（`newest_put=true → false`）

- **语义精确**：`put_overwrite`（`src/keydir/keydir.cpp:559-574`）的 accept 条件
  `cur.file_id < file_id`（input < output）结构性恒真，**与 `biggest_file_id_` 解耦**
  —— 正是原 bug 根源（旧 `newest_put=true` 要求 `file_id >= biggest_file_id_`，
  roll 后即假）。
- **无 TOCTOU 数据丢失窗口**：sealed input file 不可能收到新 entry（put 只写 active
  file，file_id 单调递增）。`stuck_file_ids`（`merger.cpp:138-143`）是
  defense-in-depth，理论上不可达。
- **回归测试正确触发原 bug**：`ConcurrentWriterRollDuringMergeNoDataLoss`
  （`tests/merge_concurrent_writer_test.cpp:258-335`）并发 put + roll（`max_file_size=256`
  频繁 roll）+ 重开验证冷键存活。bug 版本下立即失败。
- **无其他 unlink 旁路**：input unlink 仅在 `cask.cpp:2576-2577`，由 stuck 检查守护；
  output cleanup（`cleanup_partial_outputs`）由 `any_applied` flag 守护。

### ✅ meta v3 + CRC32

- **CRC 正确**：覆盖 `[0,14)`（magic + version + mode + 向量配置 + reserved），
  自身在 `[14,18)`，最后写。短文件由 `f.gcount() != kMetaFileSize` 检测；满长损坏由
  CRC 检测；magic 损坏由 `memcmp` 检测。
- **v2 backward-compat 正确**：`read_meta`（`meta_file.cpp:66-84`）对 v2 跳过 CRC 校验，
  v3 才校验。写端恒写 v3，软迁移。
- **field.schema 单版本假设**（`kVersion=1`）保守可接受，未知版本硬 fail。

### ✅ HNSW seqlock + RCU 回收

- **标准 C++20 seqlock 模式**：odd-in / even-out + release fence + acquire load。
  无 `relaxed` 错位。
- **读者真 lock-free**：只读 seq 计数，不写共享 cacheline（hub 节点不再乒乓）。
- **RCU via `std::atomic<std::shared_ptr<HnswIndex>>`**（`search_layer.hpp:513`）回收
  正确，无 leak / UAF。控制块 refcount 即 grace period。
- **无 CAS 故无 ABA**：所有 publish 点用无条件 `store(release)`。
- **`clone_live` 快照一致性**：由单写者不变量保证（`clone_live` 即写者，不与 `insert`
  并发；`search_layer.hpp:506-508`）。

### ✅ S13-F8 — fstats UAF 修复（RCU 指针表）

- 旧：`fstats_[idx]` 直接访问 deque，并发 `emplace_back` 可能重分配 block 表 → UAF。
- 新：RCU 指针表 `fstats_ptrs_`（`atomic<AtomicFStats**>`）release-publish；读者
  `fstats_slot(idx)` acquire-load；旧数组保留（`fstats_ptr_arrays_`）避免 in-flight UAF。
- 闸门：`fstats_size_.load(acquire)` 读者须先检查 `idx < size`。
- TSan 证据已记录在注释。

### ✅ 锁序 — 干净

- **keydir 内部**（`keydir.hpp:219` 文档化）：shards 升序 → `meta_mu_` →
  `fstats_grow_mu_`。全代码一致遵循。
- **`write_mu_` 与 keydir 锁不交叉**：merge 走 keydir `shared_mutex` 而非 `write_mu_`，
  无函数先持 keydir 分片锁再要 `write_mu_`。
- **SearchLayer `fields_mu_`**：标准 double-check locking（shared → unique），无跨锁
  依赖。
- **无 callback 持锁死锁**：`parallel_scan` callback 无锁调用；IndexPool reducer 不持
  Cask 锁，只调 thread-safe 的 `search_` 方法。
