# S45-6 基准报告：索引管线去全局顺序化

日期：2026-11-17 · 机器：192.168.3.13（8 核，共享机，测量时空闲）· 构建：gcc 14
Release + LTO · 基线：7.0.3（`4d3b506`，`git archive` 出的独立源码树）

## 1. 方法

- 同一份基准源码（只用公共 API）分别链接 7.0.3 与 S45 树的静态库，交替运行两轮
  （base / new / base / new），两轮差异约 ±5%。源码见附录。
- 文本：词表 5000，每篇 12 词，Whitespace 分词；`sync_every_n = 0`。
- 「end2end」= 从开始写到 `flush_index()` 返回（全部文档可检索）。
- 索引池分片数 = `index_workers` 默认值（本机 8）。

## 2. 结果（两轮均值；S45 列为最终默认参数：分片队列 512）

| 场景 | 7.0.3 | S45（队列 2048） | **S45（队列 512，默认）** |
|---|---|---|---|
| 单写线程 20 万篇，end2end | 52 k 篇/s | 69 k 篇/s | **67 k 篇/s** |
| 4 写线程 20 万篇，end2end | 49 k 篇/s | 69 k 篇/s | **73 k 篇/s** |
| 8 写线程 20 万篇，end2end | 52 k 篇/s | 65 k 篇/s | **66 k 篇/s** |
| 4 写线程 10 万篇 + 32 维向量 | 5.4 k 篇/s | 5.6 k 篇/s | **5.7 k 篇/s** |
| put_batch 1 万 × 10 | 55 k 篇/s | 66 k 篇/s | —（同 2048，未单测） |
| 20 万篇库 close | 130 ms | 255 ms | **195 ms** |
| 20 万篇库重开（含首次 flush） | 1 390 ms | 525 ms | **505 ms** |
| 10 万篇向量库重开 | 680 ms | 105 ms | **108 ms** |
| 持续 4 写线程下 `flush_index` 延迟 | **饿死**（10 s 内一次都未返回） | p50 235 ms / max 350 ms | **p50 46 ms / max 179 ms** |
| 10 万篇 + 2 写线程下 `checkpoint()` | 中位 74 ms | 中位 213 ms | **中位 94 ms** |

## 3. 解读

1. **文本索引吞吐 +30～45%**：分词与倒排写入从单 reducer 变为 8 分片并行；写路径
   （`write_mu_` + 组提交）成为新瓶颈，故 1/4/8 写线程差别不大。
2. **向量吞吐持平**：HNSW 仍单写者（串行道），与 7.0.3 的 reducer 同为瓶颈——设计
   预期（§9 明确不做 HNSW 多写者）。
3. **重开 2.7×（文本）/ 6×（向量）**：同 LSN 重放幂等跳过 + 重放起点跳过已覆盖记录，
   不再全量重新分词、不再重写段。
4. **读屏障不再饿死**：7.0.3 的谓词「在途数归零」在持续写入下几乎不成立；S45 只等
   调用时刻之前分配的 LSN。
5. **队列容量校准**：读屏障与 checkpoint 的延迟 ≈ 在途积压 ÷ 应用吞吐。队列 2048
   时 8 分片积压上限 1.6 万任务（≈ 230 ms），512 时 4 千（≈ 60 ms）；吞吐不变（写
   线程被背压的时机提前，但应用线程始终有活）。默认取 512。
6. **close 仍慢于 7.0.3（195 vs 130 ms）**：原先归因于「每分片一个 building 段、
   close 封口落盘 8 个段文件」。S45-7 已改为 checkpoint / close 时先把各分片小段合并
   再落盘（见 §6），段文件数大幅减少，**但 close 耗时没有可测变化**（同场 A/B：合并前
   193～223 ms，合并后 199～244 ms，在噪声内）——上述归因不成立。真正原因见 §7：
   **不是结构性回退**，是 20 万篇这个测点恰好落在 7.0.3 自动 checkpoint 节奏的有利
   位置（close 时它只剩 3 392 篇未封口，S45 剩约 1.2 万篇）。
7. **checkpoint 略慢（94 vs 74 ms）**：S45 先等调用时刻之前的 LSN 全部应用（保证
   「覆盖到调用时刻」语义），再独占保存；同上，多段封口也有贡献。

## 4. 未做 / 后续候选

- 跨库公平性（设计 §8-7）：本轮基准为单库；未见需要按库配额的证据，未实现。
- 分片数调参：沿用 `index_workers`；写路径已是瓶颈，增加分片无收益。
- 段数收敛：已做（S45-7，见 §6）。
- close 比 7.0.3 慢：已查清，测点偶然性，非回退（§7）。「自动 checkpoint 改以触发点为
  锚」**不做**（2026-11-17 用户定）：只换来 close 耗时可预测、不降均值，却会打破
  「恢复重放窗口 ≤ auto_checkpoint_min_docs」的设计上限（S31.5）。基准测 close 时应
  先手动 checkpoint 或取多个测点。

| `-Werror` 库构建（g++） | 通过 |

收口过程中 sanitizer 与循环测试抓到并已修复两处问题：① 新执行器「归零递减 → 取锁
notify」窗口的 heap-use-after-free（TSan）；② 查询缓存「计算 → put」TOCTOU（既有
缺陷，真并发应用下约 5% 丢 1～2 篇文档）。

`SeqGate.PairedReadsNeverTorn` 的偶发失败（约 1%）已查清：失败的全是对照组断言
（不经闸的裸读 `torn_raw > 0`，用来证明测试有分辨力），闸本身在 gcc / clang Debug /
TSan 下累计数百次加压重复从未读到不成对数据、TSan 无告警。对照组是概率性的，调度不利
时固定 5 万次写内可能一次都没撞上。测试改为写满 5 万次后对照组仍为 0 则继续写到采到
为止（20 s 封顶），900 次重复（600 次加压）0 失败。

## 6. S45-7：checkpoint / close 时分片小段先合并再落盘

`TextPlugin::flush_building` 把各分片的 building 段按文档数从小到大贪心装箱（每组
≤ 65 536 篇，即正常阈值封口段的上限），组内经 `merge_segments_v2` 直接写成一个段
文件；单段组与合并失败的组退回原逐段封口。同场 A/B（同一基准源码分别链接合并前 /
合并后的 text_plugin 静态库）：

| 场景 | 合并前 | 合并后 |
|---|---|---|
| 10 万篇 + 1 次 checkpoint 后段文件数 | 9 | 2 |
| 20 万篇 + close 后段文件数 | 11 | 4 |
| 4 写线程 20 万篇、每 2.5 万篇 checkpoint 一次后的在线段数 | 8 | 1 |
| 同上，2 词查询 top10 p50 / p99（3 轮） | 58～60 / 158～187 µs | 40～41 / 122～153 µs |
| close（bulk 场景，2 轮） | 193～223 ms | 199～244 ms |
| checkpoint 中位（10 万篇 + 2 写线程，2 轮） | 84 / 109 ms | 126 / 109 ms |
| 写入吞吐（bulk 1/4/8 写线程） | 61～71 k 篇/s | 64～71 k 篇/s |

结论：收益在查询（在线段数少，p50 约 −33%）与文件数；close / checkpoint / 写入
吞吐无可测变化（单轮 checkpoint 126 ms 与另一轮 109 ms 同为噪声范围）。

## 7. close 耗时调查（S45 vs 7.0.3）

方法：两棵树的 `Cask::close` 与 `save_checkpoint_paired` 打同样的分段计时（环境变量
开关，调查后已撤除），独立的 close 基准（4 写线程写 N 篇 → `flush_index` → 计时
close）。

1. **20 万篇时差异全在 BM25 落盘**：7.0.3 为 10 ms，S45 为 73 ms；docmap（17 对 23 ms）、
   OKI 快照（33 对 43 ms）差距小，其余收尾 7.0.3 反而更长。
2. **BM25 落盘耗时 ∝ close 时未封口的文档数**，而这取决于最后一次自动 checkpoint
   落在哪：
   - 7.0.3 的自动 checkpoint 按 LSN 精确落在 65 536 / 131 072 / 196 608，20 万篇时 close
     只剩 3 392 篇；
   - S45 以 checkpoint 的**覆盖水位**（暂停时刻的连续完成前缀，略落后于触发点）作为
     下一次的锚，节奏逐次前漂（约 6.5 万 / 12.6 万 / 18.8 万），20 万篇时 close 剩
     约 1.2 万篇（BM25 落盘 67 ms）；25 万篇时有的轮次只剩 753 篇（9 ms），有的剩约
     6 万篇（132 ms）——取决于暂停时刻的应用积压，**有随机性**。
3. **跨测点**（ms，各 2 轮）：

   | 篇数 | 7.0.3 | S45 |
   |---|---|---|
   | 15 万 | 107 / 110 | 162 / 173 |
   | 20 万 | 127 / 140 | 202 / 201 |
   | 25 万 | 215 / 223 | 166 / 178（另一批次 298 / 313） |
   | 30 万 | 407 / 257 | 344 / 334 |

   7.0.3 自身也随测点在 107～407 ms 间波动；两者互有胜负。
4. **对照：close 前先 checkpoint + sync（两边都没有待封口文档）**：20 万篇 114～131 对
   126～129 ms，25 万篇 163～169 对 171～177 ms——基本持平。docmap / OKI 两段 S45 仍
   多几 ms，但写出的文件字节数一致（docmap 5 868 603 对 5 868 605，OKI run 合计
   3.68 MB 相同），perf 自身 CPU 占比也一致，属共享机 I/O 计时噪声量级。
5. 排除项：段文件数（§6）；分片阈值均摊（每分片 65 536 / 分片数 封口，实验后 close
   无改善，已撤回）。

结论：S45 close 没有结构性变慢；§2 表里「close 195 vs 130 ms」是单一测点的偶然结果。
